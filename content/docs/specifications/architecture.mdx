## Technical stack

The platform is built as **independently deployable microservices**, each owning its own
database and communicating **synchronously over REST**. This page is the contract every
`tc-*` service spec refers to.

| Concern | Choice |
| --- | --- |
| Language / framework | **JDK 25 LTS, Spring Boot 4.0+** (Spring Security 7, Spring Data JPA) |
| Service model | microservices — one bounded context per service, private datastore, no shared DB |
| Inter-service comms | **synchronous REST** via `RestClient` — no broker, no message bus |
| Edge | **Kong** API gateway (`tc-api-gateway`) |
| External providers | Cybersource, Visa Direct, PVCB — synchronous HTTPS / SFTP |
| Build & tooling | **Maven**, IntelliJ IDEA, MySQL Workbench, Flyway (migrations), Insomnia, Testcontainers |
| Datastore | per-service **MySQL 8.4 LTS** (+ standby — see [durability](#data-durability--primary--standby-hadr)); Redis for sessions/counters |

> **Version policy.** Use **JDK 25 LTS** (Spring Framework 7 / Boot 4 recommend JDK 25+ for
> production), **Spring Boot 4.0+ / Spring Security 7**, and **MySQL 8.4 LTS** (8.0 reaches
> EOL April 2026; 9.x is short-support Innovation). Spring releases get ~13 months of OSS
> support — budget a yearly upgrade.

> **Data ownership.** Each service owns its data and exposes it only through its REST API; a
> service never reads another's database. Consistency is **synchronous within a call**;
> reconciliation is the safety net for the T+n settlement.

## Services

| Service | Role | DB |
| --- | --- | --- |
| `tc-api-gateway` | Kong edge — partner auth, edge limits, single public 3DS callback, admin forwarding | — |
| `tc-cardload-service` | **Orchestrator** — fraud (Cybersource DM) + 3DS (Payer Auth) + **Visa Direct AFT/reversal/adjustment** + authorization limits. *(Merged from the former cardload + card-network.)* | `cardload` |
| `tc-settlement-service` | **Visa settlement reconciler** — ingest the file, parse it, and match each line to the authorization + prefunding legs; report breaks (scheduled batch). **No ledger — PVCB is the book of record.** | `settlement` |
| `tc-admin-service` | Admin backend — Spring Security, RBAC, limits config, audit, dashboards | `admin` |
| `tc-admin-portal` | Flutter admin front-end | — |

## Synchronous interaction model

Everything is **request/response**. There is no broker, outbox, or event bus.

| Interaction | Style |
| --- | --- |
| PVCB → Kong → `tc-cardload-service` (start a top-up) | sync HTTP (final result, or a 3DS `redirectUrl` + `/top-up-status` polling) |
| `tc-cardload-service` → Cybersource / Visa Direct / PVCB Core Banking | sync HTTPS (mTLS + MLE to Visa) |
| `tc-settlement-service` → `tc-cardload-service` (read auth/prefunding legs for reconciliation) | sync REST |
| `tc-admin-service` → services (push limit config, read dashboards) | sync REST |

Conventions every call follows:

- **`X-Correlation-Id`** is set by the gateway and propagated unchanged on every hop (it is
  the OpenTelemetry trace id) — see [traceability](#transaction-traceability).
- **`Idempotency-Key`** on every mutating call, so retries are safe.
- **Resilience:** bounded timeouts, retry-with-backoff on idempotent operations, circuit
  breakers, and **fail-closed** for money movement (reject when a control can't be evaluated).

What is **asynchronous but not message-driven**:

- The **human 3DS challenge** — returns via the gateway's single public callback endpoint.
- **Settlement reconciliation** — a **scheduled batch** (settlement lands T+n); it reads and
  writes synchronously.

## The top-up flow (synchronous orchestration)

`tc-cardload-service` orchestrates with blocking calls — there is no saga/event choreography:

1. **Edge:** PVCB → Kong → `POST /v1/topups`, returns `202`.
2. cardload: eligibility (Visa **PAAI FTAI**) → **Decision Manager** (Cybersource) → **Payer
   Authentication** (Cybersource; a challenge returns a redirect URL to PVCB → client).
3. On 3DS pass (via the public callback), cardload enforces **authorization limits**, **records
   the Visa daily FX rate** (the settlement reference), then calls **Visa Direct AFT pull** —
   now an **in-process** step.
4. On approval, cardload calls **PVCB Core Banking** to prefund, then **records the prefunding
   outcome locally** and completes the top-up — there is no ledger to post to.
5. cardload returns the outcome in the response (or, for a 3DS challenge, a `redirectUrl`);
   PVCB polls `/top-up-status` for anything not finished inline. No webhook.
6. **T+n:** `tc-settlement-service` (scheduled batch) fetches the settlement file, reads the
   authorization + prefunding legs from cardload, and **matches each line** (on the Visa
   `transactionIdentifier`), reporting any break.

**Compensation:** if prefunding fails after the AFT, cardload **immediately reverses the AFT
in-process** (a synchronous Visa reversal) — no cross-service coordination needed.

## Reliability & correctness

- Within a service, a **DB transaction** is the unit of consistency.
- Across services, **idempotency keys** plus the **exactly-once Visa pattern** (unique STAN,
  GET-status-on-timeout, never blind-resend) prevent double money movement.
- **Reconciliation is the end-of-day safety net** — it proves every settled transaction ties
  back to a real authorized + prefunded top-up, catching anything the synchronous path missed.
- **Fail closed** on money movement.

> **Trade-off of going synchronous.** A downstream outage now affects the in-flight call
> (mitigated by timeouts, retries, and the reconciliation safety net) rather than being
> absorbed by a queue. The win is far less moving machinery — no broker, outbox, inbox,
> schema versioning, or eventual-consistency windows — which suits a small team and the
> client's preference for a synchronous structure.

## Transaction traceability

Every transaction must be reconstructable end-to-end. Three identifiers carry the trace:

| Identifier | Scope | Where it lives |
| --- | --- | --- |
| `correlation_id` | **One trace** for the whole top-up = the **OpenTelemetry trace id** | Stamped by the gateway; propagated via **`X-Correlation-Id`** on every REST hop and log line, and returned to PVCB on the response |
| `transaction_ref` | **The business top-up** (`topup-<uuid>`) | The spine across **every service's database** |
| Provider ids | The external leg | Cybersource `decisionId` / `authenticationTransactionId`; Visa `transactionIdentifier` / STAN / RRN / `statusIdentifier`; settlement `settlement_id` |

Rules:

- The gateway **MUST** assign `correlation_id` once and propagate it unchanged; services
  **MUST NOT** regenerate it. It is also returned to PVCB so the partner can trace.
- **Every transaction-scoped row MUST carry both `transaction_ref` and `correlation_id`**
  (child rows may FK to an aggregate that carries them).
- **Reconstruct** a transaction by querying each service DB by `transaction_ref`, pulling
  logs/traces by `correlation_id`, and following provider ids to the external legs. The
  reconciliation service bridges the Visa `transaction_identifier` back to `transaction_ref`
  via its `auth_leg` read model.

## Data durability — primary + standby (HA/DR)

Each service owns a **primary MySQL 8.4** database **and a standby replica — the "backup
database"** — maintained by **MySQL replication**, not application dual-write.

- **Replication:** semi-synchronous for the money services (RPO ≈ 0), or managed **Multi-AZ**.
- **Backups + PITR:** automated snapshots + **binlog point-in-time recovery**, retained per
  policy, with periodic **restore drills**.
- **Failover:** promote the standby; **RTO** of minutes. The append-only audit and reconciliation
  tables replicate too, preserving the full trace across a failover.
- **Supporting stores:** Redis (sessions/counters) runs HA; these are recovery dependencies,
  not systems of record — the durable truth is each service's MySQL + its standby.

| Service | Primary | Standby (backup) | Replication |
| --- | --- | --- | --- |
| tc-cardload-service | `cardload` | `cardload-standby` | semi-sync / Multi-AZ |
| tc-settlement-service | `settlement` | `settlement-standby` | **semi-sync** (reconciliation results + as-is staging) |
| tc-admin-service | `admin` | `admin-standby` | async acceptable |

> Backups protect against corruption/deletion (PITR); the standby protects against instance
> loss (failover). You need **both**.

## System-wide data map (DBML)

All service databases on one canvas, **schema-namespaced per service** (`cardload.*`,
`settlement.*`, `admin.*`) and grouped with `TableGroup`. Columns are trimmed to keys
and correlation fields — full column-level DBML is in each service spec. `tc-api-gateway`
(Kong) and `tc-admin-portal` (Flutter) have no database.

- **Solid relationships within a service** are real foreign keys.
- **Cross-service links are logical** — no cross-database FKs. They are synchronous
  correlations over the shared **`transaction_ref`** and Visa **`transaction_identifier`**.
