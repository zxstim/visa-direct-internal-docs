## Purpose & scope

`tc-cardload-service` orchestrates a single top-up **synchronously**. It receives a verified
request from [`tc-api-gateway`](/docs/specifications/tc-api-gateway), screens and authenticates
the card with Cybersource, executes the **Visa Direct AFT pull**, **records the Visa FX rate**,
drives prefunding, **records the outcome**, and **returns the result in the response** — there is
**no webhook push back to PVCB**.

> **Why no webhook.** PVCB does not want an asynchronous push. Their concern: if this service
> has an issue mid-flow, a pushed update could be lost and the top-up on PVCB's side would hang
> **pending forever**. So the contract is: **every PVCB request gets a response**, and PVCB
> **polls** [`/v1/top-up-status`](#interaction-model--synchronous-response--polling) for any
> outcome that cannot complete inside that response.

It is built as **five modules** behind a synchronous orchestrator:

| Module | Responsibility | Cybersource / Visa |
| --- | --- | --- |
| **Tokenization** | exchange the Flex transient token → TMS id **+ network token (VTS)**; supply the right token to each leg (PAN never stored) | Cybersource Flex / TMS · VTS |
| **Decision Manager** | fraud screening — **toggleable** | Cybersource Decision Manager |
| **Payer Authentication** | 3-D Secure (setup → enrol → step-up → validate) | Cybersource Payer Authentication |
| **Visa Direct** | **FTAI eligibility** (pre-screen, runs first), AFT pull, reversal, adjustment, OCT refund; authorization limits | Visa Direct / PAAI |
| **Foreign Exchange** | fetch & cache Visa's daily FX rate; **snapshot it per transaction at authorization** as the settlement reference | Visa Foreign Exchange Rates |

> Capture is **client-side (Flex)** and only **tokens** flow through `tc-*` — the Cybersource
> token on the Cybersource legs, a **network token + cryptogram** on the Visa legs. The **raw PAN
> never enters `tc-*`**, which **minimizes PCI scope**.

## Resilience & fault tolerance

This service moves money, so it is built to a hard standard:

> **No combination of external-API outages — or a crash of this service itself — can lose
> money, double-charge a card, or leave PVCB without a definitive answer.** The worst possible
> outcome is a **delay**, never a loss or an ambiguity.

That property is not luck; it falls out of a small set of deliberate design decisions:

| Design decision | What it buys |
| --- | --- |
| **Persist-first, write-ahead status** — the `topup` row is written before any work, and the status is committed **before** each external call ([Status tracking](#status-tracking-persist-first)) | the exact stage is always on disk — the **database is the source of truth, not the call stack or the network** |
| **Synchronous + polling, no push** | PVCB never waits on us to call them — they poll [`/top-up-status`](#interaction-model--synchronous-response--polling), which always returns a definitive state |
| **One money-moving step** — only the Visa AFT pulls funds; everything before it is retry-safe | the blast radius of any failure before the AFT is **zero** |
| **Exactly-once Visa** — unique STAN, GET-status-on-timeout, **never blind-resend**, reversal-to-cancel | an uncertain AFT is **resolved, never guessed** → no double pull, no stranded funds |
| **Autonomous reaper** — recovery runs independently of the request thread/process | stuck transactions converge to a terminal state **even if the original request, thread, or process is gone** |
| **Money state recorded only after the provider confirms** | a crash never records a phantom approval or advance — and there is no ledger to leave one in |
| **Reconciliation backstop (T+n)** | the settlement file is the final proof that every settled transaction ties to a record |

### Tolerance under cascading failure

The guarantee holds under **any** of these failures — including all of them at once:

| Failure | What happens | Money at risk? | PVCB sees |
| --- | --- | --- | --- |
| **Cybersource down** (tokenization / DM / 3DS) | pre-money failure, recorded with `error_code`, `retryable: true` | **none** — no money moved | `FAILED` (retryable) → retry as a new top-up |
| **Visa Direct down** | AFT can't start (no money moved) → `FAILED`; or an in-flight AFT stays `AFT_PROCESSING` and is resolved by GET-status / reverse when Visa returns | **none** — never double-pulled or lost | `FAILED`, or `AFT_PROCESSING` (keep polling) |
| **Both Cybersource *and* Visa down** | the transaction is parked at a **known non-terminal stage**; the reaper retries with backoff until a provider recovers, then resolves it | **none** | a non-terminal status — **never "pending forever"** |
| **This service crashes** (any stage) | persisted status + STAN let the reaper resume exactly where it left off — `< AFT_SUBMITTED` → `FAILED`; `AFT_SUBMITTED` → GET-status/reverse; `AFT_APPROVED` → finish prefund or reverse | **none** — provably reversed or booked | the last committed status, then a terminal one |
| **All of the above simultaneously** | the record survives (persist-first); no money moves without a confirmed AFT; the reaper resolves when providers recover; reconciliation catches any residual mismatch | **none unaccounted** | always a definitive status within a bounded time |

The mechanics — error classification, in-call record-and-propagate, the AFT exactly-once path,
the crash-recovery-by-stage table, and the guarantees summary — are in
[Error handling & recovery](#error-handling--recovery-money-movement-safe).

## Technical stack

JDK 25, Spring Boot 4.0+ (Maven), Spring Data JPA on MySQL 8.4 LTS. **All integration is
synchronous** via `RestClient`: the module clients (Cybersource Tokenization, DM, Payer Auth;
Visa Direct + the **Visa Foreign Exchange Rates API** over mTLS + MLE) and PVCB Core Banking
(prefunding). It does **not** call `tc-settlement-service` — the reconciler reads the legs from
here. No messaging/broker. See [Architecture](/docs/specifications/architecture).

### Build order (recommended)

Build the **integration layer before the orchestration.** The two providers are the hard, risky
part (auth, mTLS, MLE, cryptograms, their latency and quirks) — and per
[Scalability](#scalability--throughput) they're also the real throughput ceiling — so prove them
in isolation first, then layer the flow on top:

1. **Integrate the provider clients first.** Pull in the **Cybersource Java SDK** for the
   Cybersource legs (clone the
   [samples](https://github.com/CyberSource/cybersource-rest-samples-java) to validate sandbox
   credentials), and **write a small Visa client** — a thin `RestClient` wrapper — for the Visa
   legs (**FTAI**, **AFT**, **FX**), since those VDP APIs have no turnkey Java SDK. Get auth
   working end to end (HTTP Signature / JWT for Cybersource; mTLS + `x-pay-token` + MLE for Visa).
2. **Test the clients on their own.** Exercise each call against the sandbox — happy path, error
   responses, timeouts — and capture the **latency baselines**
   ([Testing § provider benchmarks](#testing-requirements)) *before* any flow logic exists. A
   green, benchmarked client layer is the foundation everything else sits on.
3. **Build the described flow on top.** Only then compose the
   [orchestration](#orchestration--lifecycle) — **persist-first, exactly-once, fail-closed** — over
   clients you already trust.

## Interaction model — synchronous response + polling

The whole design turns on one rule: **PVCB never waits on a push from us.** Two cases:

**1. No 3DS challenge (frictionless, or an early reject).** `POST /v1/topups` runs the entire
flow inline — tokenize → FTAI → DM → 3DS (frictionless) → limits → fees → FX snapshot → AFT →
prefund → record — and returns the **final result** in the (possibly multi-second) response. PVCB has its answer; no polling
needed.

**2. 3DS challenge required.** A human must authenticate (OTP / in-app / biometric / passkey),
which can take minutes — too long to hold a connection. `POST /v1/topups` returns immediately:

```json
{ "transactionRef": "topup-…", "status": "CHALLENGE_REQUIRED",
  "redirectUrl": "https://3ds.tc.example/step-up/…", "expiresAt": "2026-06-11T10:07:00Z" }
```

PVCB renders the `redirectUrl`; the customer authenticates at the issuer; the frontend calls
back `POST /v1/topups/{ref}/3ds-complete`, which **resumes the synchronous flow** (validate →
limits → fees → FX snapshot → AFT → prefund → record). **PVCB learns the outcome by polling
`GET /v1/top-up-status/{ref}`.**

### `/v1/top-up-status` (the poll endpoint)

PVCB polls this for any transaction; it **always returns a definitive state** covering both the
3DS stage and the Visa stage:

| `status` | Meaning | Terminal |
| --- | --- | --- |
| `PROCESSING` | initial inline processing (brief) | no |
| `CHALLENGE_REQUIRED` | 3DS challenge issued; awaiting the customer | no |
| `CHALLENGE_EXPIRED` | customer did not complete 3DS within the window | **yes** |
| `REJECTED_FRAUD` | Decision Manager rejected | **yes** |
| `REJECTED_3DS` | 3DS not authenticated | **yes** |
| `REJECTED_LIMIT` | over an authorization limit | **yes** |
| `AFT_PROCESSING` | Visa Direct AFT in flight | no |
| `DECLINED` | Visa AFT declined | **yes** |
| `APPROVED` | AFT approved, prefunded, booked | **yes** |
| `FAILED` | unrecoverable system error | **yes** |

> **Never "pending forever".** Because PVCB only polls (never depends on our push), and a
> **reaper** job forces every stuck transaction to a terminal state on a TTL — a
> `CHALLENGE_REQUIRED` past its window → `CHALLENGE_EXPIRED`; an AFT with an unknown result is
> resolved via the Visa **GET-status / reversal** path → `APPROVED`/`DECLINED`/`FAILED` — every
> poll converges to a terminal status within a bounded time, regardless of any fault here.

## Status tracking (persist-first)

The **very first thing** `POST /v1/topups` does — **before any module runs** — is persist a
`topup` row with `status = CREATED` (plus `idempotency_key`, `correlation_id`, amount, and the
tokenized card) in its own committed transaction. From that instant the transaction is
queryable: a `/top-up-status` poll already returns `PROCESSING`. PVCB is therefore **never
blind**, even if this service crashes a millisecond later.

Thereafter **every stage transition is committed as it happens** — there is no in-memory-only
state. At each step a module:

1. Sets `topup.status` to the **in-progress** stage and appends a `topup_state_transition` row
   **before** the external call — e.g. `FRAUD_SCREENING` before calling Decision Manager,
   `AUTH_SETUP`/`AUTH_ENROLLMENT` before Payer Auth, `AFT_SUBMITTED` before the Visa AFT.
2. Sets `topup.status` to the **result** stage after — e.g. `AFT_APPROVED` / `AFT_DECLINED`.

So at any moment `topup.status` is exactly where the transaction is, and
[`/top-up-status`](#interaction-model--synchronous-response--polling) is a **pure read** of it
(mapped to the PVCB-facing value). The append-only `topup_state_transition` table keeps the
**full ordered history** (from/to/reason/timestamp) for audit and support — every stage the
transaction passed through, not just the current one.

> **Why write the in-progress stage *before* the external call?** It is the money-movement
> safety anchor: if the service dies while Visa is processing, the row already says
> `AFT_SUBMITTED`, so the reaper resolves it via the Visa **GET-status / reversal** path rather
> than guess. **The persisted status is the source of truth, not the call stack.**

Example timeline (challenge path), each line a committed status:

```
t0  CREATED            ← persisted by POST /v1/topups, before any module
t1  AFT_ELIGIBILITY → FRAUD_SCREENING → AUTH_SETUP → AUTH_ENROLLMENT
t2  AWAITING_CHALLENGE ← POST returns redirectUrl;   /top-up-status = CHALLENGE_REQUIRED
t3  AUTH_VALIDATION    ← 3ds-complete callback
t4  LIMIT_CHECK → AFT_SUBMITTED                       /top-up-status = AFT_PROCESSING
t5  AFT_APPROVED → PREFUNDING → COMPLETED             /top-up-status = APPROVED
```

## Module 1 — Tokenization (Cybersource Flex / TMS + network token)

- PVCB's frontend captures the card with **Flex Microform**, producing a short-lived
  **transient token (JWT)**; this is sent in `POST /v1/topups` — the **PAN never reaches
  `tc-*`**.
- The module exchanges the transient token for a **TMS instrument identifier** (durable,
  storable) and a **card fingerprint** for limit logic.
- **Network tokenization.** Cybersource TMS acts as a **Visa Token Service (VTS) token
  requestor**: it provisions a **network token** (a token-PAN / DPAN that VisaNet recognizes) and,
  per transaction, mints the **AFT cryptogram**. That — **not** the raw PAN, and **not** the
  Cybersource vault token (which VisaNet doesn't understand) — is the credential for the **Visa**
  legs.
- **What each leg gets:** **Cybersource** legs (DM, Payer Auth) take the **Cybersource token**
  (`tokenInformation` / TMS id); **Visa** legs (FTAI, AFT) take the **network token + cryptogram**.
  The real PAN is held by Cybersource / VTS — never by `tc-*`.
- Only the TMS id + **network-token reference** + masked `last4`/`brand`/`exp` + fingerprint are
  persisted (no PAN, no cryptogram at rest).

## Eligibility — Funds Transfer Attributes Inquiry (FTAI)

**Before any Cybersource risk/auth step**, the orchestrator asks Visa whether the card can
actually take an **AFT pull** — so we **fail fast** on an ineligible card instead of paying for a
fraud screen and challenging the customer for nothing.

**API — Visa Payment Account Attributes Inquiry (PAAI) · Funds Transfer Attributes Inquiry
(FTAI).** `POST /paai/fundstransfer/v5/attributesinquiry` (VDP, mTLS + `x-pay-token`; the inquiry
uses the **network token** — the same credential as the AFT, **not** the raw PAN). It returns the
account's funds-transfer attributes; the ones that gate this flow:

| Attribute | Use |
| --- | --- |
| **AFT Cross-Border / Domestic Participant** | **the gate** — can this card receive an Account Funding (pull)? a tourist's foreign card is the **cross-border** case |
| **Card Type Code** (credit / debit / prepaid / …) | enforce allowed card types; risk / limit signal |
| **Billing Currency Code** | sanity-check vs the top-up; feeds the [FX](#module-5--foreign-exchange-visa-fx-rates) pair |
| **Issuer Name / Country Code** | corridor / BIN / geo policy |
| **Fast Funds / OCT Participant** | relevant to the **refund** (OCT) path later, not the AFT |

- **Position:** `tokenize → FTAI → DM → 3DS → limits → fees → FX → AFT`. It runs **after
  tokenization** (so it has a usable card credential) and **before the Cybersource risk/auth
  steps** — this is the [`AFT_ELIGIBILITY`](#orchestration--lifecycle) stage, going to
  `REJECTED_INELIGIBLE` if the card can't take an AFT. (The PAN never reaches `tc-*`; the inquiry
  uses the **network token**. Confirm PAAI accepts a network token with your Visa rep — some
  inquiry APIs still key on the underlying PAN, in which case the lookup runs inside
  Cybersource / VTS, not here.)
- **Read-only, pre-money, retry-safe.** An FTAI failure moves no money; **fail closed** — if
  eligibility can't be determined, reject (retryable) rather than authorize an unverified card.
- **Not a throwaway call:** the returned attributes (card type, issuer country, billing currency)
  are **persisted** (via `visa_call`, `operation = PAAI`) and **reused** downstream — by limits
  (currency / BIN / card-type policy), FX (billing currency), and as a risk signal for DM.

## Module 2 — Decision Manager (fraud, toggleable)

Standalone screening via the Risk API.

- **Endpoint:** `POST /risk/v1/decisions` — `ACCEPT` / `REJECT` / `REVIEW`.
- Device fingerprint (`deviceInformation.fingerprintSessionId`) collected on the PVCB client.
- `REVIEW` per `onReview` (default `HOLD` → no funds move); feedback via
  `POST /risk/v1/decisions/{id}/marking`.
- **Disabled** (`fraudScreening.enabled = false`) → no DM call.

## Module 3 — Payer Authentication (3-D Secure 2.x)

Three calls plus the customer step-up.

| Step | Endpoint | Result |
| --- | --- | --- |
| Setup / device data collection | `POST /risk/v1/authentication-setups` | `referenceId` + DDC URL |
| Check enrollment | `POST /risk/v1/authentications` | `AUTHENTICATION_SUCCESSFUL` (frictionless) / `PENDING_AUTHENTICATION` (challenge) / failed |
| Validate results | `POST /risk/v1/authentication-results` | final `cavv`/`eci`/`xid`/`dsTransactionId` |

### How the challenge works (verified against Cybersource)

When enrollment returns `PENDING_AUTHENTICATION`, Cybersource returns a **step-up JWT** with a
`stepUpUrl` and the **return URL baked in**. This service composes a **`redirectUrl`** to a
**tc-hosted 3DS page** that runs the step-up (Cardinal iframe) and listens on the return URL.
On completion the issuer ACS **POSTs the `TransactionId`** to that return URL; the page calls
`POST /v1/topups/{ref}/3ds-complete`; this service calls **`/risk/v1/authentication-results`**
with the `authenticationTransactionId` to get the authoritative outcome, and — if
`AUTHENTICATION_SUCCESSFUL` — carries `cavv`/`eci`/`xid`/`dsTransactionId`/`specVersion` into
the AFT. *(This matches the flow you described and the Cybersource Payer Authentication
docs.)*

### Issuer challenge methods — handled uniformly

Issuers run several challenge methods today; **the merchant does not implement any of them** —
the issuer's ACS runs the method inside the Cybersource step-up, and we only render the step-up
and read the result:

| Method | What the customer sees | Notes |
| --- | --- | --- |
| **OTP** (SMS/email) | enters a code in the ACS challenge UI | traditional; fast |
| **OOB** (out-of-band) | **approves in their banking app**; the ACS shows a "waiting" screen | no code in our flow; can take longer |
| **Biometric** | Face ID / fingerprint prompt in the issuer app | reduces OTP reliance |
| **Passkey / FIDO (SPC)** | WebAuthn / Secure Payment Confirmation | EMV 3DS 2.3+; a two-AReq variant that Cybersource abstracts |

Implications we **do** handle: the step-up window and the `/top-up-status` poll must tolerate
**longer waits** (OOB/biometric/SPC can take a minute+), and the `CHALLENGE_REQUIRED` TTL
(`expiresAt`) should be generous (e.g. 5–10 min) before the reaper expires it. Beyond that, all
methods converge on the same `3ds-complete` → `authentication-results` path.

## Module 4 — Visa Direct (AFT, limits, corrections)

After 3DS passes, this module enforces limits and calls Visa Direct directly.

- **Authorization limits** (authoritative gate): per-transaction max, currency/BAI/MCC
  allowlists, per-card daily sum + velocity, per-BIN ceiling, global circuit breaker (Redis
  counters); **fail closed** if unevaluable.
- **AFT pull** — `POST /visadirect/fundstransfer/v1/pullfundstransactions` carrying STAN, RRN,
  BAI, MCC, amount, the **network token + AFT cryptogram** (from Cybersource / VTS), and the 3DS
  `cavv`/`eci`. `actionCode == "00"` →
  approved (→ prefunding); else declined.
- **Reversal** (`reversefundstransactions`, ≤ ~24h) — triggered by prefunding failure /
  cancellation / uncertain timeout. **Adjustment** — amount correction. **Refund** (OCT,
  ≤ ~30 days) — past the reversal window.
- **Exactly-once:** unique **STAN** from the `Idempotency-Key`; **never blind-resend** on
  timeout — `GET .../pullfundstransactions/{statusIdentifier}`, else reverse.
- **VDP connectivity:** mTLS + `x-pay-token` + **MLE**. Card **eligibility** is checked up front by
  [FTAI](#eligibility--funds-transfer-attributes-inquiry-ftai) — before Cybersource — not here.

## Module 5 — Foreign Exchange (Visa FX Rates)

The platform pulls in one currency (e.g. **USD**) and funds the local account in **VND**, so a
**USD→VND conversion** sits in the middle. This module captures the **Visa exchange rate at
authorization** and records it against the top-up, so settlement reconciliation later has the
**exact rate we priced on** as its reference.

**Source — Visa Foreign Exchange Rates API.** `POST /forexrates/v2/foreignexchangerates` (VDP,
mTLS + `x-pay-token`) returns Visa's **daily** conversion rate for a currency pair, optionally
applying a **markup** (our FX margin). The request carries the source/destination currency and a
source amount; the response carries the **base conversion rate**, the **markup rate**, the
**total conversion rate**, the **converted destination amount**, and the rate's **as-of
date/timestamp**. (See the
[Visa FX Rates reference](https://developer.visa.com/capabilities/foreign_exchange/reference).)

**Daily cache, per-transaction snapshot.** Visa publishes the rate **once per day**, so we do
**not** call Visa on the money hot-path:

- A **scheduled job** fetches the daily rate for each configured pair (with the contracted
  markup) and caches it in `fx_rate_daily` (and Redis). It refreshes on Visa's publication
  cadence; a cache miss/staleness triggers an on-demand fetch.
- At **authorization**, the orchestrator **snapshots** the applicable daily rate into an
  `fx_quote` row bound to the `topup` — base rate, markup, total rate, source/destination
  amounts, and Visa's as-of timestamp. **This snapshot is the settlement reference.**

**Optional quote/lock for the customer.** PVCB can call
[`POST /v1/fx-quotes`](#service-api) first to fetch a quote from the cache (`quoteId`, rate,
converted amount, `expiresAt`), show the tourist the VND they'll receive, then pass `fxQuoteId`
on `POST /v1/topups`. At authorization the **locked quote** becomes the recorded snapshot; if no
quote was supplied (or it expired), the orchestrator snapshots the **current daily rate**. Either
way the rate is **pinned before the AFT** (persist-first), so the value shown, used, and recorded
are identical.

**Resilience.** The snapshot reads from the **daily cache**, so a Visa-FX outage does **not**
block top-ups while a same-day rate exists. **Fail closed** only if no valid rate is available
(we cannot price the conversion) — recorded as a **retryable, pre-money** failure. The FX call is
**read-only** and never moves money.

**Settlement linkage.** The recorded rate is the **expected** basis: at T+n the settlement file
reveals what Visa actually settled, and
[`tc-settlement-service`](/docs/specifications/tc-settlement-service) reconciles settled-vs-expected
within tolerance — the residual gap is **FX drift / gain-loss**. The funded VND on
`prefunding.fx_rate` derives from this snapshot.

## Fee configuration (pre-authorization)

> **Placeholder — endpoint not yet designed.** This reserves the step and its position in the
> flow. The `tc-admin-service` fee endpoint, the fee-rule schema, the cache/refresh mechanism, and
> the persisted breakdown are **TBD** and get filled in when admin's fee module is specced.

**Just before authorization**, the orchestrator queries
[`tc-admin-service`](/docs/specifications/tc-admin-service) for the **current fee configuration**
and applies it to price the top-up. Fees are a set of **fixed** and **dynamic** components:

| Kind | Meaning | Examples |
| --- | --- | --- |
| **Fixed** | flat amounts that don't vary with the transaction | a per-top-up service fee, per currency |
| **Dynamic** | computed at request time from the transaction | a percentage of the amount, tiered bands, per-BIN / corridor / card-type, an FX margin |

- **Position in the flow:** `… → limits → fees → FX snapshot → AFT → …`. Fees are resolved with
  the [FX snapshot](#module-5--foreign-exchange-visa-fx-rates) so the **authorized amount and the
  customer's fee breakdown** reflect live config and the day's rate.
- **Endpoint (placeholder):** `GET /api/config/fees` on `tc-admin-service` — **TBD**; the
  request/response and the fee-rule model are not yet designed.
- **Freshness (recommended, TBD):** fee config changes rarely (admin maker-checker), so — like
  authorization limits — it should be **cached / pushed** rather than fetched from admin on every
  top-up, keeping it off the money hot-path. Exact mechanism (push vs short-TTL pull) is decided
  with the endpoint.
- **Fail closed:** if the fee configuration can't be resolved, **reject** the top-up — we cannot
  price it — recorded as a **retryable, pre-money** failure.
- **Recorded:** the **applied fee breakdown** (which fixed + dynamic components, and the amounts)
  is persisted against the `topup` for **audit and settlement reference** (schema TBD with the
  endpoint).

## Orchestration & lifecycle

There are **two synchronous entry points** that run the money movement: `POST /v1/topups`
(frictionless path) and `POST /v1/topups/{ref}/3ds-complete` (challenge path). Both end by
updating the status that `/top-up-status` returns.

```
CREATED → AFT_ELIGIBILITY (FTAI) ──ineligible──▶ REJECTED_INELIGIBLE
  └▶ FRAUD_SCREENING (skipped if DM off) ──REJECT──▶ REJECTED_FRAUD / ──REVIEW──▶ IN_REVIEW
       └▶ AUTH_SETUP → AUTH_ENROLLMENT
             ├─ frictionless ───────────────┐
             ├─ challenge ─▶ AWAITING_CHALLENGE  (return redirectUrl; PVCB polls)
             │      ├─(3ds-complete)─▶ AUTH_VALIDATION ─ fail ─▶ REJECTED_3DS
             │      │                          └─ success ─┐
             │      └─(TTL elapsed)──▶ CHALLENGE_EXPIRED   │
             └─ failed ─────────────────────▶ REJECTED_3DS │
       (frictionless success) ────────────────────────────┤
                                                            ▼
                                              LIMIT_CHECK ──over-limit──▶ REJECTED_LIMIT
                                                  └▶ AFT_SUBMITTED ──declined──▶ AFT_DECLINED
                                                        │  └ timeout ─▶ STATUS_QUERY ─▶ (approved|declined|reverse)
                                                        └─ approved ─▶ AFT_APPROVED
                                                              └▶ PREFUNDING ──failed──▶ REVERSAL_SUBMITTED ─▶ REVERSED → FAILED_PREFUND
                                                                    └─ completed ─▶ COMPLETED
   (post-completion) AFT_APPROVED ─ adjust ─▶ ADJUSTED · refund(>24h) ─▶ OCT_SUBMITTED ─▶ REFUNDED
```

Because the AFT runs **in-process**, the prefunding-failure compensation (reverse the AFT) is a
direct synchronous call.

### Frictionless vs challenge (Decision Manager ON)

```
frictionless:  POST /v1/topups → tokenize → FTAI → DM → 3DS(frictionless) → limits → fees → FX → AFT → prefund → record → FINAL RESPONSE
challenge:     POST /v1/topups → tokenize → FTAI → DM → 3DS(enroll=challenge) → RESPONSE{redirectUrl}
               … customer authenticates …
               POST /3ds-complete → validate → limits → fees → FX → AFT → prefund → record → FINAL RESPONSE   (+ PVCB polls /top-up-status)
```

With `fraudScreening.enabled = false`, the DM step is simply absent.

## Endpoint design & orchestration

The product has **three interaction flows**; they map onto a deliberately small set of endpoints.
The guiding rule is **one endpoint per lifecycle, not one per flow.** Adding a card and running a
top-up are different lifecycles (one moves no money and has no `topup` row) — so they are separate
endpoints. But a top-up with a freshly entered card and a top-up with a saved token are the *same*
lifecycle that merely **starts from a different credential** — so they share one endpoint.

### The three flows

| # | Flow | Endpoint | Moves money? |
| --- | --- | --- | --- |
| 1 | **Add card only** — tokenize a card for later use | `POST /v1/payment-instruments` | no |
| 2 | **Top up with full card** (optional *save card*) | `POST /v1/topups` | yes |
| 3 | **Top up with a saved card** (tokenized) | `POST /v1/topups` | yes |

Flows 2 and 3 are **one endpoint**, differentiated by a `paymentSource` discriminator in the body:
tokenization normalises both to a TMS / network token in the **first step**, after which the
orchestration is byte-for-byte identical. Splitting them into two routes would duplicate the entire
money state machine for no benefit.

### How many endpoints — recommendation

**Four endpoints carry the three flows end-to-end** — the two above, plus two that the
synchronous-response + polling + 3DS interaction model *forces* (a challenge top-up cannot complete
without them):

| Endpoint | Why it's needed | Status |
| --- | --- | --- |
| `POST /v1/payment-instruments` | Flow 1 — tokenize-only. New vs the Flex-only baseline (see PCI note) | **new** |
| `POST /v1/topups` | Flows 2 & 3 — the top-up | exists |
| `POST /v1/topups/{ref}/3ds-complete` | resume the challenge path after the customer authenticates | exists |
| `GET /v1/top-up-status/{ref}` | the poll endpoint — the whole "no webhook" contract hinges on it | exists |

The remaining endpoints in [Service API](#service-api) — `POST /v1/fx-quotes`,
`POST /v1/topups/{ref}/prefunding-callback`, and the corrective
`/reversal · /adjustment · /refund` — are **supporting**, delivered with their respective modules
(FX, prefunding, Visa Direct corrections).

> **PCI scope note.** Flow 2 (and optionally Flow 1) accept **full card details** on the wire, so
> the raw PAN now enters `tc-cardload-service`. This **widens PCI scope** — the service is in the
> **CDE / SAQ-D** — versus the Flex-only baseline in
> [Card data handling & PCI](#card-data-handling--pci), which still holds for the transient-token
> path. Accepted deliberately. Regardless of entry mode, the PAN is exchanged for a token at
> **step 1** and **never persisted** (only TMS id + network-token ref + masked fields + fingerprint
> are stored), and is **never logged**.

### `POST /v1/payment-instruments` — add card / tokenize-only (Flow 1)

Turn a card into a reusable, AFT-eligible token. **No money movement, no `topup` row, no reaper** —
a different lifecycle from the top-up, which is why it is its own resource (it has no state in the
`topup_status` machine).

- **Request** — a `paymentSource`, one of:
  - `{ "type": "CARD", "number", "expMonth", "expYear", "cvv"? }` — full card (PCI path), or
  - `{ "type": "TRANSIENT_TOKEN", "transientTokenJwt" }` — Flex-captured (PCI-minimised path);
  - plus `customerRef`.
- **Steps:**
  1. **Tokenize** → exchange for a **durable TMS instrument identifier** and provision a
     **network token (VTS)**; derive `last4` / `brand` / `exp` + card fingerprint.
  2. **FTAI eligibility** *(recommended)* → record whether the card can take an AFT pull and its
     attributes (card type, issuer country, billing currency). This is the **AFT-relevant** validity
     signal and moves no money — and the only pre-money check worth running here (a purchase-rail
     auth would only validate a rail this product never uses).
- **Response** — `{ instrumentId, networkTokenRef, last4, brand, expMonth, expYear, eligibility? }`.
  Persist the instrument (no PAN). The returned token is what Flow 3 sends back.

### `POST /v1/topups` — the top-up (Flows 2 & 3)

Requires an `Idempotency-Key` header; optional `fxQuoteId`.

- **Request** — `amount`, `currency`, `customerRef`, `deviceFingerprintSessionId`, optional
  `fxQuoteId`, and a discriminated `paymentSource`:
  - `{ "type": "CARD", "number", "expMonth", "expYear", "cvv"?, "saveCard"?: boolean }` — Flow 2, or
  - `{ "type": "TOKEN", "instrumentId", "networkTokenRef" }` — Flow 3
    (also accepts `{ "type": "TRANSIENT_TOKEN", … }` for a Flex-captured fresh card).
- **Orchestration** (persist-first; each in-progress stage committed **before** its external call):
  1. **Persist `CREATED`** — write the `topup` row first (idempotency key, correlation id, amount,
     masked card). A `/top-up-status` poll already returns `PROCESSING`.
  2. **Tokenize** — normalise the `paymentSource` to a TMS + network token. `saveCard: true` ⇒
     create a **durable** instrument (reusable later, exactly like Flow 1's output) and echo the
     token ref in the response; otherwise a transaction-scoped token suffices.
  3. **FTAI** → `AFT_ELIGIBILITY`; ineligible → `REJECTED_INELIGIBLE`.
  4. **Decision Manager** *(if enabled)* → `FRAUD_SCREENING`; `REJECT` → `REJECTED_FRAUD`,
     `REVIEW` → `IN_REVIEW`.
  5. **Payer Authentication** → `AUTH_SETUP` → `AUTH_ENROLLMENT`:
     - **frictionless** → continue inline;
     - **challenge** → persist `AWAITING_CHALLENGE` and **return `CHALLENGE_REQUIRED` + `redirectUrl`**
       (PVCB polls; the flow resumes at `/3ds-complete`).
  6. **Visa Direct part — limits → fees → FX snapshot → AFT pull → prefunding.**
     *(See [Visa Direct part — pending](#visa-direct-part--pending).)*
  7. **Record outcome** and return the final result.
- **Responses** — either the **final result** (`APPROVED` / a terminal `REJECTED_*` / `DECLINED` /
  `FAILED`), or, on a challenge, `{ status: "CHALLENGE_REQUIRED", redirectUrl, expiresAt }`.
  Re-delivery with the same `Idempotency-Key` returns the **current state**, never a second top-up.

### `POST /v1/topups/{ref}/3ds-complete` — resume after the challenge

The tc-hosted 3DS page calls this once the customer authenticates. Steps: **validate** the result
(`/risk/v1/authentication-results`) → `AUTH_VALIDATION` (fail → `REJECTED_3DS`) → **Visa Direct part**
*(see [pending](#visa-direct-part--pending))* → record. Returns the final result; PVCB also learns
it by polling. It is the target of the gateway's **public** callback and is **DB-backed**, so it may
land on any instance.

### `GET /v1/top-up-status/{ref}` — the poll

A **pure read** of `topup.status` mapped to the PVCB-facing value (see
[the poll endpoint](#v1top-up-status-the-poll-endpoint)) — a cheap single-row indexed read that
supports `ETag` / `304`. Always returns a definitive state; never blocks; never moves the state
machine itself (the reaper does that).

### Visa Direct part — pending

> portion shared by `POST /v1/topups` and `POST /v1/topups/{ref}/3ds-complete` (step 6 above) —

> **prefunding** — together with the corrective endpoints
> (`POST /v1/topups/{ref}/reversal · /adjustment · /refund`) is being finalised by the colleague

## Error handling & recovery (money-movement-safe)

Money is involved, so the rule is: **nothing is unaccounted for.** Every failure is recorded
on the transaction, surfaced to PVCB, and — if it touches money — resolved to a known terminal
state.

### The one line that moves money

Only the **Visa AFT pull** pulls funds. Everything before it — tokenization, Decision Manager,
3DS, limits, eligibility — **moves no money and is safe to fail and retry**. Everything from
the AFT onward is the danger zone, governed by the exactly-once rules below. The **persisted
status is the boundary marker**: anything `< AFT_SUBMITTED` is safe; `AFT_SUBMITTED` and beyond
needs reconciliation with Visa before it can be called failed.

### Error classification

| Class | Examples | Handling |
| --- | --- | --- |
| **Transient** | timeout, 5xx, 429, connection reset | bounded retry-with-backoff **for pre-money steps only**; for the AFT → GET-status / reverse, **never blind-retry** |
| **Permanent** | 4xx validation, issuer decline, auth rejected | record + return a decline/error; not retryable as-is |
| **Uncertain** | no response / unknown outcome of the **AFT** | the money-movement recovery path (below) — the transaction stays `AFT_PROCESSING` and is resolved, never guessed |

### Inside the synchronous call — record, then propagate to PVCB

When a Cybersource or Visa call fails within the request:

1. **Classify.** For transient **pre-money** errors, retry up to N with backoff inside the call.
2. **Record the error state.** Set `topup.status` to the right terminal failure
   (`FAILED` / `REJECTED_*` / `AFT_DECLINED`), write `error_code` + `reject_reason` + `retryable`,
   append a `topup_state_transition` (with the reason), and log the call (`visa_call` for Visa;
   the module tables for Cybersource). Nothing is in-memory-only.
3. **Return a structured error** so PVCB can inform the customer:

```json
{ "transactionRef": "topup-…", "status": "FAILED",
  "errorCode": "CYBERSOURCE_UNAVAILABLE", "retryable": true,
  "message": "Temporary problem, please try again." }
```

- `retryable: true` ⇒ **no money moved** — the customer may retry (PVCB submits a **new** top-up
  with a **new** `Idempotency-Key`).
- `retryable: false` ⇒ a real decline / permanent error — do not retry.
- For an **uncertain AFT**, the call does **not** return a terminal failure — it returns
  `AFT_PROCESSING`, and PVCB **polls** `/top-up-status` (it must not retry, or it risks a second
  pull).

### The AFT — exactly-once on an uncertain outcome

The status is already `AFT_SUBMITTED` (written **before** the call). On timeout / no response,
**never blind-resend** (see [Module 4](#module-4--visa-direct-aft-limits-corrections)):

1. **GET-status** by `statusIdentifier` (`GET .../pullfundstransactions/{statusIdentifier}`) →
   `AFT_APPROVED` or `AFT_DECLINED`.
2. If still indeterminate → submit a **reversal** (safe — reversing a non-existent pull is a
   no-op at Visa) → `REVERSED` → `FAILED`. No funds are ever left pulled.

### Recovery after a crash — by persisted stage

Because we persist-first and write the in-progress status before each call, a crash leaves the
DB at a known stage. A **reaper / recovery job** (independent of the request thread) scans
non-terminal transactions past a threshold and resolves them:

| Status at crash | Money moved? | Recovery |
| --- | --- | --- |
| `< AUTH_VALIDATION` / `LIMIT_CHECK` | no | → `FAILED` (`retryable`); customer retries as a new top-up |
| `AWAITING_CHALLENGE` past TTL | no | → `CHALLENGE_EXPIRED` |
| **`AFT_SUBMITTED`** | **unknown** | Visa **GET-status** → `AFT_APPROVED` / `AFT_DECLINED`; if indeterminate → **reversal** → `REVERSED` → `FAILED` |
| `AFT_APPROVED` (no prefund yet) | **yes — funds pulled** | resume **prefunding**; if it fails → **reverse the AFT** → `FAILED_PREFUND` |
| `PREFUNDING` (outcome unknown) | maybe | query PVCB Core Banking by `transaction_ref`; funded → `COMPLETED`, else retry prefund or reverse |
| `REVERSAL_SUBMITTED` | reversing | re-drive the reversal (idempotent) until `REVERSED` |

### Worst case — Cybersource *and* Visa down **and** the service crashes

This is the scenario that must be airtight:

- The record persists at its last committed stage (e.g. `AFT_SUBMITTED`); PVCB polling sees a
  **non-terminal** `AFT_PROCESSING` — a known in-flight state, **not lost**, **not duplicated**.
- The reaper retries Visa **GET-status with backoff until Visa recovers**, then resolves to a
  terminal state. Because we **never blind-resend** and the record holds the STAN /
  `statusIdentifier`, there is **no double pull** and **no dropped transaction**.
- The top-up is marked `AFT_APPROVED` (and prefunding recorded) **only after the provider
  confirms** — a crash never records a pull or advance that didn't happen; there is no separate
  ledger to leave a phantom entry in.
- **Reconciliation (T+n) is the final backstop:** the Visa settlement file is the ultimate
  source of truth. [`tc-settlement-service`](/docs/specifications/tc-settlement-service)'s reconciliation
  matches **every settled line** to a `topup` record; any mismatch (settled but we recorded
  `FAILED`, or `APPROVED` with no settlement) surfaces as a **break** for manual resolution.
  Nothing settles without being tied back to a transaction.

### Idempotency & guarantees

- Re-delivery of `POST /v1/topups` with the same `Idempotency-Key` returns the **current
  state**, never a second top-up. A retry after a `retryable` failure uses a **new** key (new
  transaction).
- **Fail closed:** if an enabled control (DM, 3DS, limits, Visa) cannot be evaluated, the
  transaction is **rejected**, never advanced.

| Guarantee | Mechanism |
| --- | --- |
| The stage is always known | persist-first + write-ahead status |
| No double pull | never blind-resend the AFT |
| Uncertain AFT always resolved | GET-status → reversal |
| No phantom money state | record `AFT_APPROVED` / advance only after the provider confirms |
| Stuck transactions converge | reaper forces a terminal state on TTL |
| End-of-day proof | reconciliation ties every settlement to a record |

## Database schema

**MySQL 8.4 LTS / InnoDB, `utf8mb4`.** The `topup` aggregate carries the Visa request/response
fields (one AFT per top-up); `fraud_screening`, `payer_authentication`, `prefunding`,
`aft_correction`, `visa_call`, `limit_config`, `fx_rate_daily` + `fx_quote` (the recorded Visa
FX snapshot), and an append-only `topup_state_transition` support the modules. **No messaging
tables.** Optimistic-locked; no PAN (TMS id + network-token ref + masked fields + fingerprint); unique
`idempotency_key`.

```sql
CREATE TABLE topup (
  id                         BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  transaction_ref            VARCHAR(48)  NOT NULL,
  idempotency_key            VARCHAR(64)  NOT NULL,
  correlation_id             VARCHAR(64)  NOT NULL,
  pvcb_reference             VARCHAR(64)  NULL,
  status                     VARCHAR(40)  NOT NULL,
  amount                     DECIMAL(18,2) NOT NULL,
  currency                   CHAR(3)      NOT NULL,
  card_instrument_id         VARCHAR(64)  NULL,        -- Cybersource TMS id (never PAN)
  network_token_ref          VARCHAR(64)  NULL,        -- VTS network token reference (never PAN)
  card_fingerprint           VARCHAR(128) NULL,
  card_last4                 CHAR(4)      NULL,
  card_exp_month             TINYINT UNSIGNED NULL,
  card_exp_year              SMALLINT UNSIGNED NULL,
  customer_ref               VARCHAR(64)  NULL,
```

## Scalability & throughput

The workload is **almost entirely I/O-bound** — a request spends its time waiting on
Cybersource, Visa Direct, and short DB writes, with negligible CPU. That shapes the whole
scaling strategy: **keep the simple, correct blocking code and let virtual threads provide the
concurrency**, then **scale horizontally**, while accepting that the real ceiling is the
external providers, not this service.

### Virtual threads (JDK 25)

The service is synchronous by design (for correctness — [persist-first](#status-tracking-persist-first),
exactly-once). On platform threads that would cap in-flight requests at the pool size (a few
hundred), and with multi-second Visa calls the throughput would be tiny. **Virtual threads**
remove that cap:

- Enable with `spring.threads.virtual.enabled=true` (Spring Boot 4): Tomcat serves **each
  request on a virtual thread**, and every blocking `RestClient` / JDBC call **parks** the
  virtual thread instead of holding a carrier (OS) thread. Tens of thousands of in-flight
  blocking top-ups run on a handful of carriers.
- **No reactive rewrite** — the blocking code stays readable and matches the error/recovery
  design.
- **Pinning is no longer the footgun it was:** JDK 24's **JEP 491** stopped virtual threads
  pinning on `synchronized`, so on **JDK 25** the main hazard is gone. Still, avoid blocking
  inside `synchronized`/native frames — prefer `ReentrantLock` around any I/O.
- **Optional latency win:** use **structured concurrency** (`StructuredTaskScope`, JDK 25) to
  fan out genuinely independent provider calls on virtual threads — e.g. run **Decision Manager
  and the 3DS device-data-collection setup in parallel** — and join, shaving per-request
  latency without extra threads.

### The real ceiling is Cybersource + Visa Direct

Virtual threads let us **fully use** whatever concurrency the providers permit; they cannot
exceed it. So the service is built to respect and protect those limits, per provider:

- **Client-side rate limiting** (token bucket) sized to the **Visa Direct TPS granted for the
  BIN/program** and to Cybersource's limits — so we never get throttled or blocked upstream.
- **Bounded HTTP connection pools** to each provider (sized to its allowed concurrency), with
  **bounded timeouts**.
- **Bulkheads** (separate pools/limiters per provider) so a slow Visa doesn't starve
  Cybersource calls, and **circuit breakers** that fail fast when a provider degrades (Resilience4j).
- **Backpressure, not unbounded queueing:** when we hit a provider's ceiling or a breaker is
  open, return **`429`/`503`** to the gateway so load is shed/retried, rather than piling up
  millions of parked virtual threads behind a saturated provider.

### Don't hold scarce resources across an external call

Virtual threads are cheap; **DB connections and provider slots are not**.

- **Never hold a JDBC connection or an open transaction across a Cybersource/Visa call.** The
  persist-first model already enforces this: commit the status → release the connection → make
  the external call → commit the result. **HikariCP** is sized for the *DB's* concurrency, not
  the request concurrency.
- Keep transactions short and single-row where possible; the **DB pool and Redis (counters)**
  are the shared limits to watch — not thread count.

### The 3DS challenge consumes nothing

A major scaling property of the [redirect + poll](#interaction-model--synchronous-response--polling)
model: during the (possibly minutes-long) human 3DS challenge, **no thread and no connection
are held** — the `POST` already returned the redirect and closed. The transaction sits in the
DB as `AWAITING_CHALLENGE`. Customer think-time therefore **does not consume server
concurrency** (unlike holding a connection open for the challenge).

### Horizontal scaling

- Each request's state lives in MySQL, so instances are **stateless** — scale out behind the
  gateway/load balancer.
- **Autoscale on in-flight request count, latency, and provider-saturation** — **not CPU**
  (CPU stays low on an I/O-bound, virtual-threaded service).
- Shared state is **MySQL** (primary + standby; add a **read replica for `/top-up-status`** at
  high poll volume) and **Redis** (limit/velocity counters).

### Status-poll load

High top-up volume implies high `/top-up-status` poll volume. Keep it cheap: a **single-row
indexed read** on `transaction_ref` (optionally cached in Redis or served from a read replica),
a sane PVCB **poll cadence** (~2–3 s while in-flight), and `ETag`/conditional responses so an
unchanged status is a near-free `304`.

### Reaper at scale

The recovery [reaper](#error-handling--recovery-money-movement-safe) must scale too: scan
non-terminal transactions in **batches** on an index (`status`, `updated_at`), and **lease/claim**
rows so multiple instances don't double-process the same transaction.

### Knobs & signals

| Tune | Watch |
| --- | --- |
| `spring.threads.virtual.enabled=true`; per-provider rate limit / pool / breaker; HikariCP size; reaper batch & lease | in-flight requests, provider latency / error / **throttle (429)** rate, HikariCP saturation, Redis latency, virtual-thread **pinning** (`-Djdk.tracePinnedThreads` in non-prod), `/top-up-status` QPS, autoscaler triggers |

> **Bottom line.** Virtual threads make this service scale to the providers' limits on simple
> blocking code; rate limiting + backpressure keep it *within* those limits; horizontal scaling
> and a read replica absorb the rest. Beyond that, throughput is a **Cybersource/Visa capacity
> conversation** (TPS quotas), not a code change here.

## Failover & high availability

Two **independent** failure domains: the **stateless instances** and the **stateful database**.
A failure in either degrades to a **delay**, never a lost or double top-up — because the
[persisted status is the source of truth](#status-tracking-persist-first), PVCB **polls** (never
waits on a push), and money movement is
[exactly-once](#error-handling--recovery-money-movement-safe).

### Instance failover — active-active, not hot-standby

There is **no designated backup instance to boot up** (too slow for a money path). Capacity is
**already running**:

- **N ≥ 2 instances across ≥ 2 AZs**, all active behind the gateway/load balancer. Stateless, so
  any instance serves any request.
- **Health-gated routing.** Liveness + **readiness** probes; the LB drops an instance the instant
  it fails health or **can't reach MySQL/Redis** (readiness = fail-closed at the edge). The
  orchestrator (k8s / ASG / Nomad) restarts or reschedules it.
- **The dead instance's in-flight work is recovered, not lost:**
  - its last stage is already **committed** — the DB, not the dying process, holds the truth;
  - PVCB's next **`/top-up-status`** poll is answered by a **surviving** instance from the DB;
  - the **[reaper](#reaper-at-scale)** — running on every instance, claiming rows by **lease /
    `SELECT … FOR UPDATE SKIP LOCKED`** — reclaims the orphaned non-terminal transaction and drives
    it to terminal (GET-status → approve / decline / reverse). The dead instance's lease simply
    **expires** and a survivor takes over. *This is the "backup springing into action" — a peer,
    not a cold standby.*
  - a PVCB retry with the same **`Idempotency-Key`** lands on a survivor and returns current
    state — **never a second top-up**.
- **No sticky state:** the `/3ds-complete` callback and every poll are DB-backed, so they don't
  care which instance the original `POST` hit.
- **Graceful drain (planned loss / deploy):** SIGTERM → stop taking new work → finish in-flight
  (bounded) → deregister → exit. Rolling deploys keep **N-1** serving; no maintenance window.

> A crashed instance therefore needs **no failover action**: the load balancer stops routing to
> it, peers keep serving, and the leased reaper finishes whatever it had mid-flight.

### Database failover — primary → standby

The stateful half — the **real** "main DB + backup DB" question. See the system-wide
[data-durability policy](/docs/specifications/architecture#data-durability--primary--standby-hadr);
for this service specifically:

- **Topology:** primary **MySQL 8.4** + **standby replica** with **semi-synchronous** replication
  (or a managed Multi-AZ equivalent), in **separate AZs**. Semi-sync means the standby holds every
  **acknowledged** commit before the app sees success → **RPO ≈ 0**: a top-up PVCB was told
  `APPROVED` **cannot vanish** on failover.
- **Promotion is automatic, via a stable endpoint** (apps never hardcode the host):
  - **Managed** (RDS/Aurora Multi-AZ, Cloud SQL HA): provider auto-failover flips the endpoint —
    **RTO minutes** (Aurora ~30 s).
  - **Self-managed (cloud-agnostic):** **MySQL InnoDB Cluster (Group Replication) + MySQL Router**,
    or Orchestrator/MHA — promote the standby and keep traffic on the **Router / VIP / DNS** endpoint.
- **App behavior during the (seconds–minutes) failover window:**
  - **HikariCP** with connection validation + short timeouts detects the drop and reconnects to the
    new primary through the stable endpoint;
  - **fail closed** — while the DB is unreachable, reject new money movement with `503` (no
    persist-first → no safe money movement). `/top-up-status` **reads** may serve **degraded** from a
    **read replica** / last-known, clearly marked;
  - once the new primary is live, in-flight transactions **resume from their last committed stage**
    and the reaper mops up anything caught mid-call.
- **After failover:** rebuild the old primary as the new standby (restore HA). **Binlog PITR +
  snapshots** + periodic **restore drills** cover catastrophic loss beyond the standby.
- **Redis** (limit/velocity counters, idempotency cache) runs **HA** too; if unreachable, limits
  can't be evaluated → **fail closed**. It is a recovery dependency, not a system of record.

### Both at once

Even an instance crash **and** a primary-DB failover together degrade only to delay: persist-first
+ semi-sync = no acknowledged state lost; exactly-once Visa (STAN, GET-status, never blind-resend,
reverse) = no double pull; PVCB polling + `Idempotency-Key` = safe retries; the **leased reaper**
guarantees every non-terminal transaction reaches a terminal state once the platform recovers.

| Failure | Detection | Recovery | PVCB sees |
| --- | --- | --- | --- |
| **Instance crash** | LB health check | LB drops it; peers serve; reaper reclaims its in-flight rows | uninterrupted (polls a peer) |
| **Instance unhealthy** (DB/Redis unreachable) | readiness probe | pulled from rotation; fails closed | `503` on writes; status reads OK |
| **Primary DB down** | replication monitor / managed HA | promote standby; apps reconnect via stable endpoint | brief `503` on writes, then resumes |
| **AZ loss** | multi-AZ health | survivors in another AZ serve; DB promotes cross-AZ | bounded delay |

## Testing requirements

This service moves money on **virtual threads** across **two external providers**, so the suite
must prove the **non-functional guarantees** — not just happy-path correctness. Every property in
[Resilience](#resilience--fault-tolerance), [Error handling](#error-handling--recovery-money-movement-safe),
and [Failover](#failover--high-availability) needs a test that actively tries to break it.
**P0** = must pass before any money flows in production.

> **How we test.**
> - **Fully automated, in code.** Every requirement below is proven by **automated tests committed
>   to the repo** and run in CI with a single command — *not* by hand. **Manual tools (MySQL
>   Workbench, Insomnia) are for exploration only**, never the evidence; anything verified manually
>   must be **back-filled as an automated test** before it counts as done.
> - **Reports — commit a summary, archive the rest.** Each suite writes a **rolling summary**
>   (`reports/<suite>/summary.md`) — latest **pass/fail counts** + the **latency p50/p95/p99**
>   table — that is **committed and overwritten each run**, so progress is trackable in **small
>   diffs**. The **full per-run output** (verbose logs, JFR/pinning traces, coverage) goes to
>   `reports/<suite>/runs/<run-id>/`, which is **git-ignored** and kept as **CI artifacts** only.

### 1. Concurrency & non-blocking — the focus

Prove the blocking `RestClient` / JDBC calls **park** virtual threads instead of pinning carriers.

| Test | How | Pass criteria |
| --- | --- | --- |
| **No-block under load** (P0) | N = 10k concurrent in-flight top-ups against a **mock provider with injected latency** (e.g. 2 s) | throughput ≈ N ÷ latency; **carrier (platform) threads ≤ ~#cores**; added p99 latency negligible (requests **park**, not queue) |
| **Zero pinning** (P0) | run the load with `-Djdk.tracePinnedThreads=full` + JFR `jdk.VirtualThreadPinned` | **0 pinning events**; fix any `synchronized` around I/O (use `ReentrantLock`) |
| **No scarce-resource hold** (P0) | high concurrency with a small HikariCP pool | **no JDBC connection / provider slot held across an external call**; pool never exhausted ([persist-first](#dont-hold-scarce-resources-across-an-external-call) contract) |
| **Backpressure, not OOM** | drive past a provider's rate limit / open the breaker | returns **`429`/`503`** (load shed); no unbounded parked threads, no heap blow-up |

### 2. Provider latency & timeout benchmarks — the focus

Know what Cybersource and Visa actually cost, and derive timeouts from data, not guesses.

- **Benchmark each call against sandbox** and record **p50 / p95 / p99**: tokenization, DM,
  Payer-Auth setup/enrol/validate, **AFT pull**, **GET-status**, reversal, and **FX rate**.
- **Timeouts are derived** (≈ p99 × 1.5–2) and **documented per call**; per-provider pool and
  rate-limiter sizes are set to *measured latency × granted TPS*.
- **Regression gate (CI):** fail the build if any call's **p95 regresses** beyond a threshold vs
  the recorded baseline.
- **Slow-provider sweep:** inject 1 s / 3 s / 10 s / hard-timeout and assert the *right* branch
  fires at each (continue → GET-status → reverse → fail-closed).

### 3. Persistence & traceability — "always recorded" (the focus)

| Invariant | Test | Pass criteria |
| --- | --- | --- |
| **Persist-first** (P0) | for every accepted request, inspect the DB before the first provider call | a `topup` row exists with a **committed status** + `correlation_id` *before* any external call |
| **Crash-durable** (P0) | kill `-9` the process **before/after each boundary** (tokenize, DM, AFT submit, AFT response, prefund, FX) | the `topup` + `topup_state_transition` history survive; the [reaper](#reaper-at-scale) drives it to a **terminal** state |
| **No orphan** | exercise every path | every provider call has a `visa_call`/audit row; every transition recorded; **no in-memory-only state** |
| **No lost update** | concurrent writes to one `topup` | optimistic-lock (`version`) conflict handled — no silently dropped write |
| **Reconstructable** | terminal transactions | queryable by `transaction_ref` **and** `correlation_id`, with the **FX snapshot** present |

### 4. Exactly-once money movement (P0)

- **AFT timeout → never blind-resend:** mock Visa counts pulls; on timeout the service does
  **GET-status**, then reverses if uncertain. Assert **pull count ≤ 1**, ever.
- **Idempotency:** same `Idempotency-Key` → identical result, **one** top-up; fire **concurrent
  duplicate POSTs** → exactly one AFT.
- **Prefunding failure → AFT auto-reversed:** assert `REVERSED`/`FAILED_PREFUND` and **no stranded
  funds**.
- **STAN uniqueness** per `(acquiring_bin, transmission_date)`.

### 5. Failure injection & fail-closed (P0)

- Walk the [cascading-failure table](#tolerance-under-cascading-failure): each dependency down
  (Cybersource, Visa, **FX**, DB, Redis) and the combinations — assert correct
  `error_code`/`retryable`, **no money moved**, a **definitive** status, **never "pending forever"**.
- **Fail-closed:** when DM / 3DS / limits / FX / DB / Redis **can't be evaluated** → **REJECT**,
  never advance.
- Malformed / garbage provider responses, HTTP 5xx, connection resets, mid-write kills.

### 6. Reaper, limits, 3DS & FX

- **Reaper:** a stuck transaction at **each** non-terminal stage converges to terminal on TTL;
  **leased** reaper across multiple instances → **no double-processing** (`SKIP LOCKED`);
  `CHALLENGE_EXPIRED` fires on TTL.
- **Limits:** per-txn (**the $10 M guard**), per-card daily, velocity, per-BIN, global ceiling,
  currency allowlist; **concurrent race** on a limit → Redis counter stays correct (no overshoot).
- **3DS:** frictionless vs challenge; methods (OTP / OOB / biometric / passkey); the
  `/3ds-complete` callback lands on **any** instance; **callback-token replay rejected**; expiry.
- **FX:** daily-cache refresh; per-txn snapshot **recorded & immutable**; quote TTL/lock honored;
  **fail-closed when no rate**; the recorded rate is the basis of the funded amount.

### 7. Security / PCI (P0)

- **Automated log + payload scan:** assert **no PAN / CVV / track data / transient token / secret**
  appears in any log line or persisted column; **PAN is never stored**; the payload to Visa is
  **MLE-encrypted**; secrets come from the vault, never config.

### 8. HA / failover & load (pre-prod)

- **DB failover:** kill the primary mid-flight → **RPO ≈ 0** (an acked `APPROVED` survives), writes
  **fail-closed** during the window, transactions **resume** after promotion
  ([Failover](#failover--high-availability)).
- **Instance crash:** a peer + the leased reaper complete the in-flight work; PVCB's poll is
  uninterrupted.
- **Load / soak / spike:** sustained run at the **granted Visa/Cybersource TPS** (throughput holds,
  breakers behave); **multi-hour soak** for leaks; **spike** for autoscale + backpressure.

### Tooling & CI gates

- **Tools:** JUnit 5, **Testcontainers** (MySQL + Redis), **WireMock** for provider mocks with
  **latency/fault injection**, **Toxiproxy** for network chaos, **k6/Gatling** for load, **JFR**
  for pinning, **Pact** (or sandbox contract tests) against Cybersource + Visa.
- **Gates:** the **P0 suite blocks deploy**; the **latency-regression** gate and the **log-leak
  scan** run every build; require coverage on the **orchestrator + state machine** (no illegal
  state transitions).

## Assumptions & open questions

   `CHALLENGE_REQUIRED`/`AFT_PROCESSING`; confirm acceptable.
