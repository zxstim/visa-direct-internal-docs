## Purpose & scope

`tc-api-gateway` is the single, hardened ingress for the Visa Direct tourist top-up
platform. In the end-to-end sequence it sits between **PVCB Top up service** (the
partner bank backend) / the **tourist client** on one side, and the internal `tc-*`
services on the other. It is the trust boundary: nothing reaches `tc-cardload-service`,
`tc-admin-service`, or any other internal service without first passing the gateway's
controls.

This document specifies how to build that gateway as a **thin Spring Cloud Gateway app on
your existing JDK 25 / Spring Boot 4 stack** to satisfy four requirements:

1. **Partner authenticity** — verify every inbound request from PVCB Top up service
   using asymmetric signatures (exchanged public keys), with replay and idempotency
   protection.
2. **Authorization limits** — hard, gateway-enforced amount/velocity caps so a breach
   of PVCB Top up service cannot cascade into a fraudulent high-value auth (the "$10M
   auth" scenario).
3. **Minimal public surface** — exactly one publicly reachable endpoint (the client 3DS
   callback); every other route requires verification.
4. **Admin pass-through** — for internal admin traffic the gateway does forwarding only,
   straight to `tc-admin-service`.

A traceability map from the design review to the sections that satisfy each point is in
[Design review & traceability](#design-review--traceability).

> **Conventions.** **MUST/MUST NOT/SHOULD** are used in the RFC 2119 sense.
> "Money-movement paths" means any route that can initiate or change a top-up
> (`POST /v1/topups`, the 3DS callback). Those paths default to **fail-closed**.

## Technical stack & topology

The gateway is a **Spring Cloud Gateway** application — a thin Spring Boot service on the
**same JDK 25 / Spring Boot 4.0+ stack** as everything else, behind it the `tc-*`
microservices talking **synchronous REST** (no broker). See
[Architecture & service interaction](/docs/specifications/architecture).

> **Why Spring Cloud Gateway, not Kong.** The hard parts here — verifying PVCB's JWS and
> enforcing authorization limits — are **your business logic**; on Kong you'd write them as
> custom Lua plugins anyway. Spring Cloud Gateway gives you **routing + a filter pipeline as
> an ordinary Spring Boot app**: no separate product to operate, no Lua, no decK, and the
> custom filters are plain Java sharing the platform's libraries, config, and observability.

- **Variant:** use **Spring Cloud Gateway Server MVC** (servlet) with
  `spring.threads.virtual.enabled=true`, so the gateway uses the same blocking + virtual-thread
  model as `tc-cardload-service`. The **reactive** variant (WebFlux/Netty) is the alternative —
  more built-in filters (e.g. the Redis `RequestRateLimiter`), at the cost of the reactive
  paradigm in custom filters. Either is fine; the gateway holds no business logic to speak of.
- **Limits propagation.** When `tc-admin-service` updates the authorization limits, the gateway
  picks them up from a shared config source (a short-TTL read of the admin config API, or a
  Redis-published config) — no separate config tool.

## Where the gateway sits in the flow

The gateway has exactly four interaction points in the sequence diagram. Everything else
(`tc-settlement-service`, `PVCB Core Banking`, settlement) is **downstream of
`tc-cardload-service`** and never traverses the gateway directly.

| # | Counterparty | Direction | What crosses the gateway | Trust model |
| --- | --- | --- | --- | --- |
| 1 | PVCB Top up service | inbound | Top-up initiation (after PVCB's AML check), status queries (polls `/top-up-status`) | mTLS **+** signed payload **+** limits |
| 2 | Tourist client | inbound | "3DS challenge completed" notification | one-time signed callback token only |
| 3 | tc-cardload-service | outbound (proxy) | Forwarded top-up / 3DS-completed requests | internal network |
| 4 | tc-admin-service | outbound (proxy) | Internal admin traffic | forward-only, internal listener |

```
                 INTERNET (untrusted)                 PARTNER LINK (mTLS/VPN)          INTERNAL (trusted)
                 ───────────────────                  ──────────────────────          ──────────────────
   tourist  ──3DS callback──┐                  PVCB Top up service ──┐                   ┌─ tc-cardload-service
   (browser/app)            │                  (after AML check)     │                   │
                            ▼                                        ▼                   │
                    ┌──────────────────── tc-api-gateway (Spring Cloud Gateway) ─────────┤
                    │  public :8443            partner :9443          admin :10443        │
                    │  (1 route only)          (mTLS + JWS + limits)  (internal)          ├─ tc-admin-service
                    └───────────────────────────────────────────────────────────────────┘
                                                                                       (forward only)

   No outbound webhook — PVCB polls GET /top-up-status (inbound, partner surface) for results.
```

> The gateway is **stateless for business logic**. It authenticates, screens against
> limits, and routes. It must hold no transaction state beyond the short-lived counters
> and nonce/idempotency caches described below.

## Trust model & assumptions

The gateway's controls only make sense against an explicit threat model. Three trust
zones, and one rule that governs all of them: **a valid signature proves *origin*, not
*legitimacy of the underlying transaction*.**

| Zone | Parties | Posture |
| --- | --- | --- |
| Untrusted | internet, tourist client, the 3DS callback | authenticate per-request; never trust client assertions |
| Semi-trusted | PVCB Top up service | authenticated, but **assume it can be breached**; bound its blast radius |
| Trusted | internal `tc-*` services on the private network | mutual TLS / network segmentation |

Normative principles:

- **PVCB's AML/approval decision is untrusted input.** PVCB runs AML before the gateway;
  if PVCB is breached, that AML is bypassed while requests still carry valid signatures.
  The gateway and `tc-cardload-service` **MUST NOT** treat "PVCB approved" as a reason to
  relax screening. tc-side checks (the Cybersource fraud check already in the flow; add
  sanctions screening if not covered upstream) **MUST** run on every transaction.
- **The 3DS callback is an untrusted trigger, not a result.** The authoritative 3DS
  outcome **MUST** come from `tc-cardload-service` re-querying Cybersource (as the diagram
  already does). The gateway **MUST NOT** let "3DS passed" be asserted by the client.
- **Defense-in-depth.** Limits are enforced at the gateway **and** at downstream layers
  (see [Layered enforcement](#layered-enforcement)). The gateway is the first gate, not
  the only one.
- **Fail-closed by default** on money-movement paths (see [Failure & degradation
  behavior](#failure--degradation-behavior)).

| Threat actor | Assumed capability | Primary gateway control |
| --- | --- | --- |
| Compromised PVCB backend | mints validly-signed top-ups | per-tx / velocity / cumulative / global limits + idempotency + tc-side screening |
| Network MITM | intercept / alter in transit | mTLS (channel) + JWS (message integrity) |
| Replay attacker | resend a captured signed request | timestamp skew window + nonce store + idempotency key |
| Abusive client on the public endpoint | spam / enumerate the callback | one-time signed token + rate-limit + bot detection |
| Lateral movement to admin | reach the admin surface internally | dedicated internal surface + IP allowlist + mTLS/OIDC + audit log |

## Listener / network topology

Run three logically separate entry surfaces so "public" cannot accidentally include a
partner or admin route. The strongest isolation is to **run one gateway instance per
surface** — a `public`, a `partner`, and an `admin` deployment of the same app, each
activated by a Spring **profile** that registers **only that surface's routes**. (A single
instance with three connectors is possible, but HTTP routes don't match on port, so the
port split alone is not a security boundary — back it with network ACLs.)

| Surface | Bind | Reachable from | Routes registered |
| --- | --- | --- | --- |
| Public | `0.0.0.0:8443` (behind WAF/CDN) | Internet | `3ds-callback-public` only |
| Partner | private interface `:9443` | PVCB over VPN / VPC peering / private link | partner routes (`/v1/topups…`) |
| Admin | private interface `:10443` | internal admin network only | `admin-proxy` only |

- The Spring Boot **management/actuator port** must never be internet-exposed. Bind it to a
  management interface, protect it, and keep `/actuator` off the public surface.
- Put a WAF / DDoS layer (Cloudflare, AWS WAF, etc.) in front of the **public** surface.
- Terminate TLS 1.2+ (prefer 1.3). Because payloads are independently signed (JWS),
  message integrity survives TLS termination at an upstream load balancer.

## Requirement 1 — Verify all PVCB requests via asymmetric signatures

### What "asymmetric encryption" means here

The requirement is **authentication + integrity**, i.e. asymmetric **signatures (JWS)**,
not encryption. The terminology matters (see the [Design review](#design-review--traceability)):

- **Signing (what you need):** PVCB signs each request with **PVCB's private key**; the
  gateway verifies with **PVCB's public key**. This proves the request came from PVCB and
  was not altered, and gives non-repudiation. The body stays readable.
- **Encryption (optional add-on):** if you also need field-level confidentiality beyond
  TLS (e.g. for a PAN), encrypt those fields with the **recipient's public key** (JWE).
  Use this only for the sensitive fields, on top of signing.

So the control is: **mutual TLS for the channel + detached JWS over the message for
integrity/non-repudiation.** Use both — they defend different layers.

### Key lifecycle management

Asymmetric auth is only as strong as the key process around it. Treat keys as a managed
lifecycle, not a one-time setup.

| Stage | Requirement |
| --- | --- |
| Generate | Each party generates its keypair **inside an HSM/KMS**; the private key **MUST NOT** leave it. Algorithm **ES256** (EC P-256) preferred; **RS256/PS256** (RSA-3072) fallback. No symmetric `HS*`. |
| Exchange | Public keys are exchanged **out-of-band** over a secure channel; the recipient verifies the **fingerprint via a second channel** before trusting; record both keys (with `kid`) in a key registry. |
| Store | PVCB's **public** key is loaded into the gateway's **key registry, keyed by `kid`** (from config / a JWKS endpoint / Vault); the gateway selects it by the `kid` in the JWS header and verifies with **Nimbus JOSE+JWT**. tc's **private** key (used for **callback-token signing**) lives in **KMS/Vault** (e.g. Spring Cloud Vault) — **never** inlined in config. |
| Rotate | Every JWS/JWT carries a `kid`. Publish the **new** key and accept both **before** retiring the old one (overlapping validity → zero-downtime). Rotate every **6–12 months**. |
| Revoke | On suspected compromise, remove the `kid` from the accepted set immediately (config push/refresh), notify the partner out-of-band, and rotate. |

### Signature envelope (what PVCB must send)

Each partner request carries a **detached JWS** in a header. The signature **MUST** cover
the HTTP method, the request path, a SHA-256 hash of the body, and the anti-replay claims
— so none of them can be stripped or altered:

| Header | Contents |
| --- | --- |
| `X-JWS-Signature` | Detached JWS (`alg`=ES256, `kid`) over the canonical signing string |
| `X-Request-Timestamp` | RFC 3339 timestamp; rejected if skew > 60s |
| `X-Request-Nonce` | Unique value; rejected if seen before (Redis set, TTL = 2× skew window) |
| `Idempotency-Key` | Client-generated UUID for safe retries of money-movement calls |

Signing string (canonical): `METHOD \n PATH \n SHA256(body) \n X-Request-Timestamp \n X-Request-Nonce`.

### Replay protection & idempotency

A valid signature replayed twice is **two top-ups**. Signing alone is not sufficient for
money movement — two distinct, both-required mechanisms close this:

- **Nonce + timestamp (stops *malicious* replay).** The gateway **MUST** reject a request
  whose `X-Request-Timestamp` is outside ±60s (configurable) with `401 STALE_REQUEST`,
  and **MUST** reject a reused `X-Request-Nonce` with `409 REPLAY_DETECTED`. Nonces are
  held in Redis with a TTL of **2× the skew window**. Because both values are inside the
  signed string, an attacker cannot edit them to dodge the check.
- **Idempotency key (enables *safe* retry).** `POST /v1/topups` **MUST** carry an
  `Idempotency-Key`. The gateway caches `key → response` for **24h** and returns the
  cached response on a retry **without re-forwarding**; `tc-cardload-service` **MUST** also
  dedupe authoritatively on the same key, persisted with the transaction record. Same key
  ⇒ same outcome, even across gateway nodes.

> The two are complementary: the **nonce** says "I have never seen this exact request";
> the **idempotency key** says "if you retry the *same logical operation*, you get the
> *same result*, not a second charge." Money movement needs both.

### Implementing verification (Java / Nimbus JOSE)

Verification is one **custom filter** on the partner routes — a `HandlerFilterFunction`
(Server MVC) that runs **before** the proxy hands off to `tc-cardload-service`. It uses
**Nimbus JOSE+JWT** for the signature and **Spring Data Redis** for nonce/idempotency. mTLS
is configured on the server (or terminated at the LB), independent of this filter.

```java
// JwsVerifyFilter — illustrative; not production code.
@Component
class JwsVerifyFilter implements HandlerFilterFunction<ServerResponse, ServerResponse> {

    private final PublicKeyRegistry keys;          // kid -> PVCB public key (config / JWKS / Vault)
    private final StringRedisTemplate redis;
    private final Duration skew = Duration.ofSeconds(60);

    @Override
    public ServerResponse filter(ServerRequest req, HandlerFunction<ServerResponse> next) throws Exception {
        String sig   = header(req, "X-JWS-Signature");
        String ts    = header(req, "X-Request-Timestamp");
        String nonce = header(req, "X-Request-Nonce");
        byte[] body  = req.servletRequest().getInputStream().readAllBytes();   // cached/buffered body

        // 1. freshness
        if (sig == null || ts == null || Duration.between(Instant.parse(ts), Instant.now()).abs().compareTo(skew) > 0)
            return error(401, "STALE_REQUEST");

        // 2. one-time nonce (atomic SET NX with TTL) — fail closed if Redis is down
        Boolean fresh;
        try { fresh = redis.opsForValue().setIfAbsent("nonce:" + nonce, "1", skew.multipliedBy(2)); }
        catch (RuntimeException e) { return error(503, "LIMIT_BACKEND_DOWN"); }
        if (!Boolean.TRUE.equals(fresh)) return error(409, "REPLAY_DETECTED");

        // 3. detached-JWS verification over METHOD\nPATH\nSHA256(body)\nts\nnonce, key chosen by kid
        String signingString = req.method().name() + "\n" + req.requestPath().value() + "\n"
                + sha256Hex(body) + "\n" + ts + "\n" + nonce;
        JWSObject jws = JWSObject.parse(sig, new Payload(signingString));      // detached payload
        ECPublicKey pub = keys.byKid(jws.getHeader().getKeyID());             // throws/null -> reject
        if (pub == null || !jws.verify(new ECDSAVerifier(pub))) return error(401, "BAD_SIGNATURE");

        return next.handle(req);   // verified -> proxy to tc-cardload-service
    }
}
```

> **Detached JWS** keeps the body out of the signature blob (smaller header, body stays the
> wire payload). Nimbus verifies it by reconstructing the payload (the signing string) and
> checking the protected header + signature. Buffer the request body once (a
> `ContentCachingRequestFilter` / wrapper) so both the verify filter and the proxy can read it.

## Requirement 2 — Authorization limits (the "$10M auth" guard)

The gateway enforces **hard caps as defense-in-depth**: even if PVCB Top up service is
fully compromised and submits perfectly-signed requests, the blast radius is bounded. A
single per-transaction cap defeats one giant auth; you also need velocity and cumulative
caps to defeat *many* medium auths, plus a global circuit breaker.

| Control | Example value (tune per Visa program / corridor) | State needed |
| --- | --- | --- |
| Per-transaction max | ≤ 5,000 USD | none |
| Currency allowlist | `USD` only (the flow is USD top-ups) | none |
| Amount sanity | > 0, ≤ 2 decimal places, numeric | none |
| Per-card daily sum | ≤ 10,000 USD / 24h | Redis counter (card fingerprint) |
| Per-card velocity | ≤ 5 / hour, ≤ 20 / day | Redis counter |
| Per-user daily sum | ≤ 10,000 USD / 24h | Redis counter |
| **Global daily ceiling** (circuit breaker) | platform-wide cap; trip + page on breach | Redis counter |

### Implementation

There is no built-in "amount limit" filter, so this is a second **custom filter**,
`AuthLimitFilter`, on the partner money-movement routes. It parses the JSON body, checks
the stateless rules (per-tx, currency, sanity), then atomically increments and checks Redis
counters for velocity, cumulative sums, and the global ceiling. Velocity (count) caps can
alternatively use the reactive gateway's built-in **Redis `RequestRateLimiter`**, or
**Bucket4j-Redis** on Server MVC — but folding them into this one filter keeps all the
money limits in one place.

```java
// AuthLimitFilter — illustrative; not production code.  Runs AFTER JwsVerifyFilter.
@Component
class AuthLimitFilter implements HandlerFilterFunction<ServerResponse, ServerResponse> {

    private final StringRedisTemplate redis;
    private final LimitConfig cfg;                  // @ConfigurationProperties, refreshed from tc-admin-service

    @Override
    public ServerResponse filter(ServerRequest req, HandlerFunction<ServerResponse> next) throws Exception {
        TopUp body = req.body(TopUp.class);         // { amount, currency, cardFingerprint, ... }

        // --- stateless rules ---
        if (body.amount() == null || body.amount().signum() <= 0 || body.amount().scale() > 2)
            return error(400, "INVALID_AMOUNT");
        if (!cfg.allowedCurrency().equals(body.currency()))
            return error(403, "CURRENCY_NOT_ALLOWED");
        if (body.amount().compareTo(cfg.maxPerTxn()) > 0)              // defeats the single big auth
            return error(403, "AMOUNT_OVER_LIMIT");

        // --- stateful counters (fail closed if Redis is unavailable) ---
        try {
            long cents = body.amount().movePointRight(2).longValueExact();
            String card = body.cardFingerprint();                     // never the raw PAN

            if (incrWithTtl("vel:card:" + card, 1, Duration.ofHours(1)) > cfg.maxCardPerHour())
                return error(403, "VELOCITY_EXCEEDED");
            if (incrWithTtl("sum:card:" + card, cents, Duration.ofDays(1)) > cfg.maxCardDailyCents())
                return error(403, "DAILY_CARD_LIMIT");
            long global = incrWithTtl("sum:global", cents, Duration.ofDays(1));
            if (global > cfg.globalDailyCeilingCents()) {
                log.error("global ceiling tripped");                   // page on-call
                return error(503, "GLOBAL_CEILING_TRIPPED");
            }
        } catch (RuntimeException e) {
            return error(503, "LIMIT_BACKEND_DOWN");                    // fail closed
        }
        return next.handle(req);
    }

    private long incrWithTtl(String key, long by, Duration ttl) {
        Long v = redis.opsForValue().increment(key, by);
        if (v != null && v == by) redis.expire(key, ttl);              // set TTL on first write
        return v == null ? Long.MAX_VALUE : v;                          // null -> treat as over limit
    }
}
```

### Layered enforcement

The edge is the **coarse first gate**, not the only one. If a future code path reaches a
service without traversing the gateway (internal call, misconfig, new integration),
edge-only limits evaporate. Enforce caps at every layer that can move money:

| Layer | Enforces | Why it's needed even with the edge |
| --- | --- | --- |
| `tc-api-gateway` (edge) | per-tx cap, currency, velocity, daily sums, global ceiling | bounds the blast radius of a PVCB breach at the boundary |
| `tc-cardload-service` | per-tx / currency / BAI / MCC / velocity / per-BIN / global ceiling | the authoritative gate — it submits the auth to Visa, so a cap here can't be bypassed |
| Visa Direct program config | scheme-level transaction & velocity limits | enforced by Visa itself; survives any tc-side bug |

## Requirement 3 — Exactly one public endpoint

Only the **client 3DS-completed callback** is reachable from the internet. Everything else
lives on the partner or admin surface and requires mTLS + signature.

### The single public route: `POST /v1/public/3ds/callback`

This is called by the tourist's browser/app, so it **cannot** use mTLS or PVCB's
signature. "Public" does **not** mean "unauthenticated":

- When `tc-cardload-service` issues the 3DS redirect, it mints a **one-time, short-lived,
  tc-signed callback token** (a JWT signed with tc's private key, `exp` a few minutes,
  bound to the specific transaction id, single-use via `jti`).
- The gateway verifies that token with **tc's public key** (a small token-verify filter,
  Nimbus), enforces one-time use (Redis `jti` set), and only then forwards to
  `tc-cardload-service`.
- The callback is a **trigger, not a source of truth.** The authoritative 3DS result comes
  from `tc-cardload-service` re-querying Cybersource (as the diagram already shows). The
  gateway/services must never trust "3DS passed" because the client said so.

Public route filters: callback-token verify (tc key + Redis `jti`) · rate-limit (per-IP +
per-token) · bot detection (at the WAF) · request-size limit · CORS (only the app origin) ·
correlation-id. **No** mTLS, **no** partner JWS.

> Enforce the "one public route" rule **structurally**: the **public instance** registers
> *only* the `3ds-callback-public` route, and a default handler returns `404` for every
> other path — so nothing else is ever served on `:8443`, regardless of config drift.

## Requirement 4 — Admin pass-through to tc-admin-service

For internal admin the gateway is a **thin reverse proxy** — no business transformation,
no limit logic, just authenticated forwarding.

- Dedicated route `admin-proxy` (`/admin/*` → `tc-admin-service`) on the **admin instance
  only**.
- Lock down with an **IP allowlist** (internal admin CIDRs) and either internal **mTLS**
  (client certs) or, if admins are humans, **OIDC SSO** (Spring Security resource-server).
- Keep the filter set minimal: auth + correlation-id + audit logging. No request rewriting
  beyond path stripping.
- Emit an immutable **audit log** (who, what, when) for every admin call to your SIEM.

| Requirement | Surface | Spring Cloud Gateway component |
| --- | --- | --- |
| Partner channel auth | partner | `server.ssl.client-auth=need` (mTLS) or LB-terminated mTLS + asserted client DN |
| Partner message auth | partner | **custom** `JwsVerifyFilter` (Nimbus JOSE) |
| Replay + idempotency | partner | `JwsVerifyFilter` (nonce/timestamp) + idempotency cache — Spring Data Redis |
| Amount limits | partner | **custom** `AuthLimitFilter` |

| Payload size | all | `BeforeFilterFunctions.requestSize(...)` |
| Public callback token | public | **custom** token-verify filter (tc key) + Redis `jti` |
| Public abuse control | public | rate-limit filter + WAF bot detection + CORS |
| Admin network lock | admin | IP-allowlist filter (`ip-restriction`-style) |
| Admin identity | admin | mTLS or Spring Security OIDC |
| Tracing & metrics | global | a correlation-id filter + **Micrometer / Actuator** (Prometheus, OTel) |

### Routes (Java `RouterFunction`)

Define routes per surface; a Spring **profile** activates only one surface's routes per
instance. Each route attaches its filters, then proxies upstream with `http(...)`.

```java
@Configuration
class PartnerRoutes {                                   // @Profile("partner")
    @Bean
    RouterFunction<ServerResponse> partner(JwsVerifyFilter jws, AuthLimitFilter limits) {
        return route("topup-create")
            .POST("/v1/topups", http("http://tc-cardload-service.internal:8080"))
            .before(BeforeFilterFunctions.requestSize(64L * 1024))   // 64 KB cap
            .filter(jws).filter(limits)                              // verify -> limit -> proxy
            .build()
        .and(route("topup-status")
            .GET("/v1/top-up-status/{ref}", http("http://tc-cardload-service.internal:8080"))
            .filter(jws)
            .build());
    }
}

@Configuration
class PublicRoutes {                                    // @Profile("public") — ONLY this route
    @Bean
    RouterFunction<ServerResponse> publicRoute(CallbackTokenFilter token) {
        return route("3ds-callback-public")
            .POST("/v1/public/3ds/callback", http("http://tc-cardload-service.internal:8080"))
            .before(BeforeFilterFunctions.requestSize(16L * 1024))
            .filter(token)
            .build();
        // a default 404 handler covers every other path on the public instance
    }
}

@Configuration
class AdminRoutes {                                     // @Profile("admin") — forward only
    @Bean
    RouterFunction<ServerResponse> admin(IpAllowlistFilter ip) {
        return route("admin-proxy")
            .route(RequestPredicates.path("/admin/**"), http("http://tc-admin-service.internal:8080"))
            .filter(ip)
            .build();
    }
}
```

(`route`, `http`, `BeforeFilterFunctions` are the Server-MVC gateway helpers; the custom
filters are the `HandlerFilterFunction` beans shown above. Confirm exact import paths against
your Spring Cloud version.)

```yaml
  endpoints.web.exposure.include: [health, prometheus]   # keep OFF the public surface
```

> Because payloads are JWS-signed, you **may** terminate mTLS at the load balancer instead
> and have the gateway assert the verified client DN from a trusted header — message
> integrity still holds end-to-end.

### Config & secrets

- **PVCB public key(s)** → the gateway's `PublicKeyRegistry`, keyed by `kid`, loaded from
  config / a JWKS endpoint / Vault. Public keys only.
- **tc private key** (callback-token signing) → **KMS/Vault** (Spring Cloud Vault), never in
  the repo or `application.yml`.
- **Limit config** → `@ConfigurationProperties` bean (`tc.limits.*`), refreshed when
  `tc-admin-service` pushes a change (a `/internal/limits/refresh` endpoint with
  `@RefreshScope`, or a short-TTL read of the admin config API).
- **Redis** is critical-path (limits + nonce + idempotency); run it **HA** (Sentinel/Cluster)
  and fail **closed** on outage (see [Failure & degradation](#failure--degradation-behavior)).

### Run & deploy

It's a normal Spring Boot service — no Kong, no decK, no Lua:

```bash
mvn -q -DskipTests package
SPRING_PROFILES_ACTIVE=partner java -jar target/tc-api-gateway.jar   # one instance per surface
# build a container the same way you build the other tc-* services; deploy via CI.
```

Routes and limit defaults live in `application.yml` in the repo (GitOps); secrets come from
Vault/env. Three deployments — `public`, `partner`, `admin` — each behind its own LB.

### Verify the controls

Smoke-test each requirement after deploy (commands illustrative):

```bash
# 1. Unsigned partner request → rejected
curl -sk https://partner:9443/v1/topups \
  -d '{"amount":100,"currency":"USD"}' -o /dev/null -w '%{http_code}\n'          # → 401

# 2. Over-limit amount → rejected even when correctly signed
curl -sk https://partner:9443/v1/topups --cert pvcb.pem \
  -H "X-JWS-Signature: $JWS" -H "Idempotency-Key: $(uuidgen)" \
  -d '{"amount":10000000,"currency":"USD"}' -w '%{http_code}\n'                  # → 403 AMOUNT_OVER_LIMIT

# 3. Replay of a used nonce → rejected (resend step 2 with the same nonce)        # → 409 REPLAY_DETECTED

# 4. Public callback needs a valid one-time token
curl -sk https://public:8443/v1/public/3ds/callback -d '{}' -w '%{http_code}\n'  # → 401
curl -sk https://public:8443/v1/public/3ds/callback \
  -H "Authorization: Bearer $CALLBACK_JWT" -d '{}' -w '%{http_code}\n'           # → 200

# 5. Admin from a non-allowlisted IP → rejected
curl -sk https://admin:10443/admin/health -w '%{http_code}\n'                    # → 403
```

## Deployment

The gateway is an ordinary Spring Boot service: **one image, run three ways.** It carries **no
database** — its only stateful dependency is **Redis** (limits, nonce, idempotency) — so it scales
horizontally as stateless replicas. For the whole-platform Docker setup see
[Deployment (Docker)](/docs/deployment); this is the gateway-specific process.

### Image

Build the same multi-stage Java image as the other services (Maven/JDK 25 → slim JRE, non-root):

```dockerfile
# tc-api-gateway/Dockerfile
# syntax=docker/dockerfile:1

WORKDIR /app
COPY pom.xml .
RUN mvn -B -q dependency:go-offline
COPY src ./src
RUN mvn -B -q -DskipTests package

ENTRYPOINT ["java","-XX:MaxRAMPercentage=75","-jar","/app/app.jar"]
```

### Three instances from one image

Production runs the image as **three independent deployments**, each activated by a Spring
**profile** that registers **only that surface's routes** (this is the structural "one public
route" guarantee), on its own port behind its own load balancer and network policy:

| Instance | Profile | Port | Exposure | Routes | TLS |
| --- | --- | --- | --- | --- | --- |
| `gateway-public` | `public` | 8443 | Internet (behind WAF/CDN) | `3ds-callback-public` only | TLS |
| `gateway-partner` | `partner` | 9443 | PVCB private link only | `/v1/topups…` | TLS + **mTLS** |
| `gateway-admin` | `admin` | 10443 | internal admin network only | `admin-proxy` | TLS (+ mTLS/OIDC) |

```yaml
  gateway-partner:

    build: ./tc-api-gateway
```

### Configuration & secrets

- **Routes** are chosen by the active **profile** — never deploy the public instance with partner
  routes registered.
- **TLS / mTLS:** mount the server **keystore** and, on the partner surface, the **truststore**
  (PVCB client-cert CA) with `server.ssl.client-auth=need`. Or terminate mTLS at the LB and pass
  the verified client DN — message integrity still holds (the body is JWS-signed).
- **Secrets** come from a **secrets manager / Vault**, injected as env/mounted files, never baked
  into the image: **PVCB public keys** (the `kid` registry / JWKS), **tc's private callback-signing
  key**, Redis credentials, keystore passwords. See [Key lifecycle](#key-lifecycle-management).
- **Limit config** is seeded in `application.yml` and **refreshed from `tc-admin-service`** (a
  refresh endpoint or short-TTL pull) — a limit change does **not** require a redeploy.
- **Redis** is critical-path and shared; run it **HA** and fail **closed** on outage
  (see [Failure & degradation](#failure--degradation-behavior)).

Three `Deployment`s (one per surface), each its own `Service` + LB + `NetworkPolicy`, ≥2 replicas,

### Rollout & operations

- **GitOps:** routes + limit defaults live in `application.yml` in the repo; deploys reference
  **immutable image tags** (built in CI, tagged by commit). No hand-editing in prod.
- **Zero-downtime:** rolling deploy **per surface** (keep N-1 replicas serving); the gateway is
  stateless, so draining is just graceful connection shutdown.
- **Key rotation:** publish the new `kid`, accept both, retire the old — a **config refresh, not a
  redeploy** ([Key lifecycle](#key-lifecycle-management)).
- **Scaling:** autoscale each surface on **in-flight requests / latency** (state is in Redis, not
  the pod). The partner surface carries the money traffic; size it for the Visa/Cybersource TPS the
  flow drives.
- **Observability:** scrape `/actuator/prometheus`; alert on signature-failure spikes, limit
  breaches, replay spikes, global-ceiling trips, and fail-closed counts.

## Failure & degradation behavior

Money-movement paths **MUST** fail closed: when a security dependency cannot be evaluated,
reject rather than let traffic through. Read-only/status paths **MAY** degrade more
gracefully.

| Dependency unavailable | Affected check | Behavior |
| --- | --- | --- |
| Redis (limits / nonce / idempotency) | amount caps, replay, idempotency | **Reject** money-movement with `503 LIMIT_BACKEND_DOWN`; do not approve unscreened |
| Signature verification (key fetch / JWS) | partner & callback auth | **Reject** with `401`; never bypass |
| `tc-cardload-service` upstream down | request processing | **Reject** with `503` + `Retry-After`; **never** auto-approve a top-up |
| Cybersource (downstream of cardload) | fraud / 3DS result | Handled by `tc-cardload-service`; the transaction **MUST NOT** proceed on an unknown 3DS/fraud result |

- **Status/read endpoints** (`GET /v1/top-up-status/{ref}`) **MAY** return a degraded/cached
  read if a non-critical dependency is down, as long as they never imply a money movement.
- Every fail-closed rejection emits a metric and, for global-ceiling/limit-backend
  failures, pages on-call.

## Cross-cutting concerns

- **PCI DSS scope.** The gateway is on the path of card data and is almost certainly in
  CDE scope. Tokenize/replace the PAN as early as possible, pass only a **card
  fingerprint** to limit logic, never log PAN/CVV/track data, and mask sensitive fields in
  all logs.
- **Observability.** Correlation-id end-to-end (a small filter sets/propagates
  `X-Correlation-Id`), **Micrometer/Actuator** metrics (auth failures, limit rejections,
  replay rejections, callback abuse, fail-closed counts) scraped by Prometheus,
  structured logs to SIEM, OpenTelemetry traces. Alert on: signature-verification failure
  spikes, limit-breach spikes, replay spikes, and global-ceiling trips.
- **Consistent error contract.** Return structured JSON errors (`{ code, message,
  correlationId }`) with stable codes; never leak stack traces, upstream identities, or
  whether a card/user exists.
- **Resilience.** Upstream health checks + circuit breaking (Resilience4j) and the
  fail-closed posture above.
- **High availability.** Deploy ≥2 instances **per surface** behind an L4 LB; Redis in HA
  (the limit and nonce/idempotency stores are critical-path).

## Design review & traceability

Overall the design is **sound and shows good security instincts** — defense-in-depth
limits at the edge, partner request signing, attack-surface minimization, and a thin admin
proxy.

### What's good — kept and reinforced

1. **Edge amount limits as defense-in-depth.** Capping at the gateway so a PVCB breach
   can't trigger a $10M auth is exactly right; the threat model (trust PVCB, bound the
   blast radius) is mature.
2. **Asymmetric signing for the partner.** Far better than shared secrets — integrity and
   non-repudiation per message.
3. **Minimizing the public surface to one route.** Good attack-surface reduction.
4. **Not trusting the client's 3DS callback** (re-querying Cybersource for the
   authoritative result). The single most important correctness property here.
5. **Admin as forward-only.** Clean separation; keeps the gateway thin where it should be.

### Gaps from the review → where they are now specified

| # | Review finding | Resolved in |
| --- | --- | --- |
| 1 | "Asymmetric encryption" → asymmetric **signatures** (JWS), not encryption | [What "asymmetric encryption" means here](#what-asymmetric-encryption-means-here) |
| 2 | Signing alone isn't enough — add replay + idempotency | [Replay protection & idempotency](#replay-protection--idempotency) |
| 3 | "One public endpoint" must still be authenticated (one-time token + rate-limit + bot) | [The single public route](#the-single-public-route-post-v1public3dscallback) |
| 4 | Don't rely on the edge as the only limit enforcement | [Layered enforcement](#layered-enforcement) |
| 5 | One big cap isn't enough — velocity + cumulative + global ceiling | [Authorization limits](#requirement-2--authorization-limits-the-10m-auth-guard) |
| 6 | Fail closed on money movement | [Failure & degradation behavior](#failure--degradation-behavior) |
| 7 | AML at PVCB is bypassable — keep independent tc-side screening | [Trust model & assumptions](#trust-model--assumptions) |
| 8 | Currency must be on an explicit allowlist | [Authorization limits](#requirement-2--authorization-limits-the-10m-auth-guard) (`allowed_currency`) |
| 9 | Plan PCI scope and `kid`-based key rotation up front | [Key lifecycle management](#key-lifecycle-management), [Cross-cutting concerns](#cross-cutting-concerns) |

### Why this is the right weight

Spring Cloud Gateway is **Apache-2.0 OSS with no edition tiers** — every control above
(mTLS, JWS verify, amount/velocity limits, single public route, admin forward) is built
from the framework plus two small custom Java filters. You avoid Kong's separate runtime,
Lua plugin SDK, decK, and admin API, and the gateway shares the platform's libraries,
config, secrets, and observability. The only real choice is the variant — **Server MVC**
(servlet + virtual threads, consistent with the rest of the backend) or **reactive**
(more built-in filters such as the Redis `RequestRateLimiter`). For a 2-dev team on a Java
stack, this is the right weight: a thin proxy you fully own, not a platform to operate.
