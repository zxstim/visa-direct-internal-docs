## Plan at a glance

Team: **2 backend (BE-A, BE-B) + 2 Flutter (FE-A, FE-B)**.

> **Focus is Phase 0 only — the next two weeks.** Build the **integration SDKs first**, test them
> in isolation, then start **Visa Direct certification**, with the **orchestration built in
> parallel**. Later phases (full rails, admin service, hardening) are deliberately out of view
> until Phase 0 lands.

Sequence — matches the
[build order](/docs/specifications/tc-cardload-service#build-order-recommended) (clients first,
test, then the flow):

1. **Integration SDKs + testing — this week (Jun 12–19).** A thin, independently-tested client
   layer per provider: **BE-A → Visa Direct** (FTAI, AFT, reversal, FX), **BE-B → Cybersource**
   (tokenization, Decision Manager, Payer Auth).
2. **Visa Direct certification — next week (Jun 22–26).** BE-A runs Visa's cert test cases against
   the already-tested Visa Direct SDK.
3. **Orchestration — meanwhile.** Once the SDKs are green, BE-B stitches the flow
   (FTAI → DM → 3DS → limits → fees → FX → AFT → prefund → record) on top — **in parallel** with
   certification, on clients we already trust.

## Phase 0 — integration SDKs → certification (Jun 12 → Jun 26)

**Why SDKs first:** the two providers are the hard, risky part (auth, mTLS, MLE, cryptograms,
their latency) **and** the real throughput ceiling — proving them in isolation de-risks everything
on top. Certification then runs against a client we already trust, and the orchestration becomes
wiring rather than discovery.

> **Estimate.** Building + testing the **SDKs this week is comfortable** for two devs in parallel.
> **Visa Direct certification next week is feasible** — the gating item is **Visa-side
> provisioning** (cert-environment access, MLE keys, AFT-program BIN), which must be in hand
> **now**, not the code. The **orchestration lands in parallel** because it sits on already-tested
> clients. "Testing" here = isolated client tests + latency baselines, not the full
> [Testing-requirements](/docs/specifications/tc-cardload-service#testing-requirements) suite.

## Assumptions & risks

1. **Visa-side provisioning is the critical path.** VDP **cert-environment** access, **MLE keys**,
   and a registered **AFT-program BIN** must be live **now** — they, not the code, decide whether
   certification can start next week.
2. **Cybersource sandbox creds needed now too** — BE-B starts the Cybersource SDK this week.
3. **SDK-first is deliberate.** Each provider client is tested in isolation before any flow logic;
   certification and orchestration then sit on clients we already trust.
4. **Certification is one dev (BE-A) — thin buffer.** A smooth **VDP connectivity** bring-up is
   what makes or breaks the cert date.
5. **"Basic testing" only.** The full Testing-requirements suite (concurrency, soak, failover)
   comes after Phase 0.
