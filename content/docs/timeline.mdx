## Plan at a glance

Team: **2 backend (BE-A, BE-B) + 2 Flutter (FE-A, FE-B)**, fully dedicated.

> **Architecture update.** `tc-card-network-service` is **merged into `tc-cardload-service`**, the
> **double-entry ledger is dropped** (PVCB is the book of record) so `tc-settlement-service` is now
> purely the **Visa settlement reconciler**, and the **messaging layer is removed** — services talk
> over **synchronous REST**. That cuts the broker/outbox/inbox plumbing *and* the ledger, so the
> Jul 15 target is a little more comfortable than the event-driven plan.

- **Phase 1 — Jul 15:** `tc-api-gateway`, `tc-cardload-service` (orchestration **+ Visa
  Direct**), and `tc-settlement-service` (**settlement reconciliation**) **functionally
  complete (no hardening)** — the end-to-end top-up works synchronously in sandbox. Flutter
  builds the full portal UI against mocks in parallel.
- **Phase 2 — Jul 30:** `tc-admin-service` backend + **portal integration**.
- **Phase 3 — after Jul 30:** hardening (security/PCI, perf, gateway custom plugins, full
  reversal/adjustment/refund, production cert).

Track split: **BE-A** = gateway + the **Visa Direct module of cardload**, then **settlement
reconciliation**; **BE-B** = the **orchestration module of cardload** (Cybersource — tokenization,
DM, Payer Auth), then **joins reconciliation** (matching + reports) once orchestration lands.
`tc-cardload-service` is built as two modules by the two devs; `tc-settlement-service` is
**reconciliation-only**. Flutter works **contract-first** against mocks. Days 1–2 both backend
devs pair on foundations, then split.

## Assumptions & risks

1. **"No hardening" is load-bearing.** Phase 1 fits only as *functional happy path* — minimal
   error handling, config-driven limits, no custom gateway plugins, no security/perf pass.
2. **External sandboxes on day 1 are the critical path.** Visa Developer (VDP) + test BIN and
   Cybersource sandbox credentials must be live from Jun 9; the AFT/3DS work and the Jul 15
   demo depend on them.
3. **Reconciliation is the long pole.** It can only be fully tested once cardload exposes the
   auth/prefunding read API (~Jul 9+); if upstream slips, recon is the
   first item to slide past Jul 15.
4. **One service, two devs.** `tc-cardload-service` is built by BE-A (Visa module) and BE-B
   (orchestration module) together — agree the internal module boundary early.
5. **Limits via config until Phase 2.** Authorization limits are seeded/config-managed until
   the admin CRUD UI ships Jul 16–30.
